## 2. 更优化、可复用的核验与处理流程

### 2.1 本次暴露的三个流程病害（均有实测证据）

1. **结论硬编码在展示层**：21 条发现写在 `App.tsx` 的 TSX 常量里，无法被程序读取、无法绑定证据、无法随 commit 自动失效。本次只能靠人工把 42 条声明重新敲进核验器。
2. **缺「反证检索」环节**：审查者读了代码却没读 `docs/DECISIONS.md` / `BACKLOG.md` / `deliverables/reviews/`。同仓库的 ADR-040 明确写着「这套不再生效」，直接推翻了报告唯一的 P0。**这是 B1 判错的根因，不是能力问题，是流程缺环节。**
3. **数字靠手写、无时间戳**：README 的 679 / 85 / 55 / 39 / 约 5MB 全部腐烂，报告又原样引用；且声明没有绑定 commit，代码变了报告不会自动标「待复核」。

### 2.2 改进方案：Claim Ledger（声明账本）+ 自动核验

| # | 做法 | 解决什么 | 本次落地物 |
|---|---|---|---|
| 1 | **声明结构化**：审计报告不再把结论写进 TSX，改为 `claims.json`：`{id, text, source, evidence_level, check, expected, observed, verdict, verified_at, commit}`。展示页只渲染 `claims.json` | 结论可被程序读、可被 diff、可被 CI 消费 | `audit_verify.py` 内 `CLAIMS` 已按此结构实现（42 条） |
| 2 | **每条声明绑定可执行检查**：`line_contains` / `regex_count` / `json_field` / `git_fact` / `exec_output` / `external_doc`；检查器异常显式标 `无法验证`，绝不静默当通过 | 杜绝「凭印象判正确」 | `audit_verify.py` 已实跑，**0 检查器异常**，输出 `audit-verdicts.json` + `.md` |
| 3 | **反证前置（新增强制步骤）**：核验开始前先跑 `grep -rn "ADR-|DEF-|已完成|已拍板" docs/DECISIONS.md docs/BACKLOG.md docs/HANDOFF.md deliverables/reviews/`，把已有决策/QA 结论组成「反证集」；任何声明与反证集冲突即直接判 `错误` | 本次 B1 的错误本可在 5 分钟内拦下 | 建议固化为 `tools/collect-counterevidence.py`，作为核验器第 0 步 |
| 4 | **数字单一真源**：README 的断言数、ADR 数、e2e 数、dist 体积由 `tools/gen-readme-stats.py` 在构建时生成，禁止手写；核验器直接读生成结果 | 修掉 679/85/55/39 这类腐烂 | 见 P-10 |
| 5 | **声明绑定 commit + 时间戳**：每条记录 `verified_at` 与 `commit`；CI 检测到 `HEAD != claim.commit` 时自动把该条标 `待复核`，不自动沿用旧判定 | 报告不会「过期还被当真」 | `run-manifest.json` 记录本次环境与命令 |
| 6 | **证据等级与运行态分离**：`runtime` 类声明必须附可复跑命令 + stdout + 环境版本；缺任一项一律降为 `无法验证`，不得与静态结论并列展示 | 避免「0 页面报错」这类孤证混进统计卡 | 见 R-06 |
| 7 | **CI 门禁**：把核验器接进 CI，产出 `audit-verdicts.json`；出现 `错误`、声明数漂移、或 `无法验证` 比例超阈值即失败；浏览器运行态声明单独进「实机复测清单」 | 审计结论持续有效，而非一次性 | 建议 `.github/workflows/claim-audit.yml` |

### 2.3 可复用方式（换仓库/换报告只需三步）

```
# 1) 解压任何审计包到工作区，安装依赖并实跑，输出统一落到 <work>/
python <work>/extract_evidence.py      # 逐行代码证据
python <work>/run_tests.py             # 跑被测仓库的测试套件
python <work>/verify_manifest.py       # 清单/引用文件/语言键
node  tools/build-dist.js --dry-run > <work>/build-dist-dryrun.log

# 2) 把报告里的每句话登记成 CLAIMS（id / text / check / expected）
# 3) 一键核验，产出机器可读判定
python <work>/audit_verify.py --repo <repo> --work <work> --out <work>
# → audit-verdicts.json（供 CI）+ audit-verdicts.md（供人读）
```

**目录约定**：`<work>/` 放证据与运行输出（本次在 `.workbuddy/audit-work/`，不进 git 的临时件）；`deliverables/reviews/YYYY-MM-DD-主题.md` 放两份正式文档；`tools/` 放需要长期复用的核验器（若苏哥确认要长期保留，把 `audit_verify.py` 从 `.workbuddy/audit-work/` 迁到 `tools/audit-verify.py` 并登记 §4）。

**与现有流程的衔接**：不另起炉灶。核验结论直接回写 `docs/BACKLOG.md` 的对应条目（如 B-38），重大口径变化走 ADR 追加，审计/评审报告按 `DELIVERABLES.md` §5.3「只追加不改写」另起日期文件。
