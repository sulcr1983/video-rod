# 下载去重链路修复（同平台不重复 / 跨平台留一份 / 索引多份）

> 日期：2026-11-09 ｜ 报告人：吴八哥 ｜ 触发：苏哥「这个系统一直没解决去重，点多几次就不断下载。同一平台不允许下载相同的，下载了也可以自动删除；不同平台保留一份，索引可以多份」
> 现场：真实库 `D:/personal/Downloads/video-rod`（71 条索引 / 61 个文件）＋ 9480 有头实例

---

## 一、结论先行

去重其实「写了两套」，但**两套都没生效**，而且在错误的位置互相抵消：

| 层 | 设计意图 | 实际故障 |
|---|---|---|
| L1 账本（`vrImgDownloaded`） | 下过的 URL 不再下 | 键是**整条 URL**（含 `x-signature`/镜像子域/`~tplv` 格式），抖音小红书每次加载都变 → 同一张图永远「没下过」 |
| L2 库内来源键（`vrFindExistingMedia`） | 库里已有同平台同一张 → 跳过 | 图片入库时 **meta 没带 `sourceUrl/mediaUrl`** → 条目没有来源键 → 永远查不到 |
| L3 内容指纹（`VRDedup`，sha256） | 跨平台同图：删副本、留引用（物理 1 份、索引多份） | ①索引重建 `mergeEntry` **不保留 sha256/isRef**；②库页根本没加载 `dedup.js`；③整理时用 `fetch(file://,DELETE)` **删不掉文件却改了库** |

一句话：**L1 判不出「同一张」，L2 没有比对依据，L3 一重建就忘、一整理还删不掉。**

## 二、逐项修复

| # | 位置 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `background.js: vrCanonMediaUrl` | 新增抖音图床归一：镜像节点（p3/p9/p26…）→ `douyinpic.com`，剥 `~tplv-*` 处理指令，忽略全部 query | `~tplv-dy-aweme-images:q75.webp` 与 `:q75.jpeg` 是同一张图，签名每次加载都变；不归一则永远判不出重复 |
| 2 | `background.js: vrImgDedupeKey` | 改用归一键，并按**平台分账**（`douyin|douyinpic.com/...`） | 苏哥口径：同平台不许重复、跨平台放行（跨平台交给内容指纹，才能留索引） |
| 3 | `background.js: vrImgBatch` | 兼容旧账本（整条 URL 仍认一次）；新账本只记「平台\|归一键」；新增 `skipped` 统计并随进度广播 | 升级后不把历史下过的重下一遍；UI 能说清「跳过 N 张」 |
| 4 | `background.js: vrImgDownload` | 入库 meta 补 `sourceUrl/mediaUrl`；重复命中返回 `skipped` | 这是 L2 失效的根因：没有来源键，库里再多条目也认不出「这张下过」 |
| 5 | `indexer.js: mergeEntry` | 保留 `sha256 / hashKind / isRef / refOf` | 重建一次索引就把指纹全丢，跨平台去重与历史合并彻底失效 |
| 6 | `indexer.js:` missing / reconcile | 引用条目（`isRef`）豁免「文件缺失」判定 | 引用条目本来就没有自己的物理文件，标 missing 会在库里留下一堆打不开的死卡 |
| 7 | `indexer.js: build(downloads)` | downloads 模式**不再丢弃**不在下载记录里的旧条目 | 严重缺陷：FSA 直写的素材（YouTube / 抖音图文 / 小红书批量）没有下载记录，一次「重建索引」就把它们抹掉（实测 109 条 → 8 条，磁盘文件还在） |
| 8 | `library.html` | 补载 `js/library/dedup.js`；设置抽屉补「内容去重 · 扫描重复」入口 | 之前库页根本没加载去重模块，`sdDupBtn` 在 JS 里存在、HTML 里不存在——入口是死的 |
| 9 | `dedup.js` | 拆出 `hashMissing()`；`compact({remove})` 改为**必须由调用方提供删除能力**，删不掉就不动库 | 浏览器对 `file://` 的 DELETE 请求会返回 ok 但根本不删文件（实测 61 个文件一个没少），先改库再删失败 = 库和磁盘不一致，比不去重更糟 |
| 10 | `trash.js` | 新增 `VRTrash.removeAt(relPath)`：走 FSA `removeEntry`，以「文件确实不存在」为成功判据 | 只有库页握着目录句柄，删除必须在这里做 |
| 11 | `background.js` | 新消息 `vrDedup.hashMissing`（只算指纹、不碰文件） | SW 能读 `file://` 算 SHA-256，库页不能；删除反过来只能在库页 |
| 12 | `app.js` | 「扫描重复」→ 扫描 → 确认 → ①SW 补指纹 ②库页合并（带 `removeAt`） | 两步各在有能力的一侧执行，避免「算了不能删 / 删了没算」 |

## 四、必须如实记的两件事

1. **我用一次测试动作触发了既有严重缺陷**：`VRIndex.build({mode:'downloads'})` 把库里 109 条抹成 8 条（磁盘文件还在）。已修（§二 #7）并用全量扫描恢复索引（71 条），指纹重新补算（58 条）。该缺陷在生产里同样存在——用户点一次「重建索引」就会中招，所以这次是**先暴露后修复**，不是新增问题。
2. **`fetch(file://, DELETE)` 是假删除**：第一次跑整理时报告「合并 48 条」，但一个文件都没删。已改成 FSA `removeEntry` 并用 `exists()` 复核；失败一律不改库。

## 五、口径与遗留

**当前口径（与苏哥三条对齐）**

- 同一平台、同一张图（含换签名/换格式/换镜像）→ **跳过**，不落盘，进度条显示「已存在跳过 N 张」。
- 不同平台、内容相同（sha256）→ **物理只留 1 份**，别的平台写一条引用索引（`isRef/refOf`），可预览、可重命名、可删除；删到最后一条引用才真删文件（R1/R2 铁律）。
- 历史遗留重复 → 库页「设置 → 内容去重 → 扫描重复」→ 确认 → 自动补指纹并合并（物理归 1，索引不动）。

**遗留**

| # | 项 | 说明 |
|---|---|---|
| 1 | 8 条 `missing` 幽灵行 | 早前测试删掉的文件留下的索引行（ADR-030 不自动删），可在库页手动删卡 |
| 2 | 大文件（>64MB）用采样指纹 | 已有设计（`hashKind='sampled'`），只用于报告、不自动合并，避免误删 |
| 3 | 未带指纹的极老条目 | 需先「扫描重复」（会自动补算，单次上限 800 条） |
| 4 | `qa-preview-page` V6 | 既有失败，单独立项 |
| 5 | 视频侧去重 | 走 `vrMediaIdentity`（site\|workId\|mediaId\|origin+pathname），本次未回归真实站点视频，建议下次抖音/微博视频实测时顺带确认 |
