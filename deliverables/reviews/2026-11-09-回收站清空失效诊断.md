# 回收站「清空后素材复活 / 列表与缩略图不消失」诊断报告

- **日期**：2026-11-09
- **报障人**：苏哥（"删除了到回收站，然后清空回收站，结果又回到主页了，然后文件可能删除了。但是列表信息和缩略图没有删除。"）
- **诊断环境**：Edge 156.0.8078（隔离 profile，`--load-extension` 载入仓库根），扩展 ID `ceogmckiinjolbbdkjfelmfcfepccabp`
- **结论**：不是「回收站没实现」，而是**删除这件事被拆成两笔互不负责的账**——物理搬文件、删索引各做各的，清空回收站又只做前一笔。任何一笔没对上，清空后就留下「文件没了、卡片和缩略图还在」的死卡。

---

## 一、先说结论（大白话）

| 现象 | 真实情况 | 定性 |
|---|---|---|
| 文件「可能删除了」 | 确实删了，`_回收站` 目录清空成功 | 正常 |
| 「又回到主页了」 | 卡片（索引条目）没被删掉，清空后主页照旧渲染它 | **缺陷** |
| 「缩略图没有删除」 | IDB `thumb` 表里该条的 blob **从来没被删过**，磁盘 `.webp` 也只是碰运气删 | **缺陷** |
| 回收站显示已清空 | `empty()` 只删 `_回收站/` 目录，一条索引、一张缩略图都不碰 | **缺陷（结构性）** |

---

## 二、实测证据（不是推断，全部有脚本可重跑）

### 证据 1：`empty()` 完全不碰索引与缩略图

`js/library/trash.js:488 empty()` 全文只做三件事：`list()` → `removeBatchDir()` → 写 oplog。**没有任何 `VRDB.deleteFiles` / `deleteThumbs`**。它默认「删到回收站时索引已经删干净了」。

实测（3 条素材 → 删 → 清空）：

```
PASS  B1 remove 移走 3 项        db=0
删后 thumb 表： 2                 ← 索引删了，缩略图 blob 还在
PASS  C1 清空后 file store 仍为 0
PASS  C4 回收站目录已空
```

`remove()` 里缩略图只调了 `VRThumbs.deleteFor()`（删磁盘 `_library/thumbs/*.webp`），**从未调用 `VRDB.deleteThumbs(['t:'+relPath])`** —— 这条 IDB blob 是永久泄漏。所以「缩略图没删」是 100% 确定的。

> 脚本：`tools/cdp-trash-empty-repro.py`（11/11 通过，断言里带 thumb 计数打印）

### 证据 2：同一文件两条索引 → 删一条，清空后留死卡（**与苏哥现象完全吻合**）

真实库里已知有 18 条 `relPath` 不带 `video-rod` 前缀的存量记录（2026-11-08 QA 审计记录在案）。前缀口径一变，同一条文件就会同时存在两条索引：

- `video-rod/B站/up/视频/a.mp4`（新口径）
- `B站/up/视频/a.mp4`（老口径）

删除只按 key 删一条，另一条原地不动。实测：

```
setup rows: 2
首屏卡片（同一文件两条索引）: 2
删掉带前缀那条： {'moved': 1, 'failed': [], 'db': 1, 'rels': ['B站/up/视频/a.mp4']}
清空回收站后： {'db': 1, 'st': 0}
刷新后： {'cards': 1, 'db': 1}     ← 文件已没了，卡片还在
```

**这就是「回到主页、文件没了、列表还在」的完整闭环。**

> 脚本：`tools/cdp-trash-dup-index-test.py`

### 证据 3：删除动作没有回滚，中途失败就是半状态

`remove()` 的顺序是：搬文件 → 写 `_manifest.json` → 删索引。三步之间没有事务、没有补偿：

- 搬成功、写清单失败 → 文件在回收站，索引还在，**回收站列表还看不到**（清单都没有）
- 搬成功、清单成功、`deleteFiles` 抛错 → 文件在回收站，索引还在，UI 只弹一句「删除失败」

后一种情况下用户再点「清空回收站」= 刚才那个死卡场景，一字不差。

### 证据 4：扫描只加不删，且 `exists` 字段不可靠

- `indexer.js:923` `build()` 只有 `putFiles(out)`，**从不删掉「扫描结果里不存在」的旧行**；扫不到的旧行最多标 `state:'missing'`（ADR-030 故意不自动删）。
- `mode:'downloads'` 靠 `if (d.exists === false) continue` 过滤已删文件。实测该字段**不可靠**：隔离实例里一次 `interrupted`、磁盘上根本没有文件的下载，`exists` 依然返回 `true`。
- `mode:'snapshot'` 读 `_library/index.json` **完全不校验磁盘**，索引里有几条就写回几条。
- `app.js:3325`：库为空时开库页会自动 `autoIndex()`（downloads → reconcile → full → snapshot 降级链）。

→ 结论：只要索引侧留了残渣，**打开库页/点扫描都可能把已删条目重新写回库里**。这条链路是 README 里「delete 掉的东西自己回来」的最可能放大器，但下载被隔离环境拦成 `interrupted`，端到端没跑通，按 D1 铁律标 **REVIEW（机制成立、触发未实测）**。

## 三、文档口径 vs 代码实现（哪里走偏了）

| 文档 | 原文口径 | 代码实际 |
|---|---|---|
| ADR-033（2026-10-24） | 批次目录 + `_manifest.json`，「恢复按清单走，IDB 清空也能恢复」 | ✅ 清单确实写了；但**只在 remove 时写，purge/empty 时从不回写索引** |
| ADR-033 第 5 条 | 需要 `readwrite` 句柄，未授权报 `LIB_E_NO_PERM` | ✅ 已实现（`ensureRW`，含陈旧句柄翻译） |
| LIBRARY-PERSISTENCE-SPEC §47 | `_回收站` 在 SKIP_DIRS 里，不参与索引 | ✅ 已实现（`indexer.js:33`） |
| 2026-11-06 红队 b-1/b-2 | 删除/改名/移动必须清缩略图 | ⚠️ **只做了磁盘 `.webp`，IDB `thumb` 表漏了**（`deleteThumbs` 存在但无人调用） |

一句话：**设计写的是「磁盘回收站 + 清单是恢复真源」，代码写成了「删索引时顺手搬文件」，两者的失败语义完全不同。**

## 四、业内成熟做法（按你的铁律先搜再写）

### 1. Immich（自托管相册，同类里最贴近我们的形态）

- 删除 = 数据库打标：`status = Trashed` + `deletedAt` 时间戳，**不做任何磁盘搬迁**；所有列表查询按状态过滤。
- 清空 = `TrashService.empty()` 流式取出所有 `Trashed` 的 id，逐个排队后台任务；`handleAssetDeletion()` 一次删掉 **原文件 + 三档缩略图 + 转码视频 + sidecar + 数据库行**。
- 关键点：**回收站的真源是数据库行，不是磁盘目录**。所以「清空 = 删行 + 级联删附属文件」，天然幂等；残留行下次再点一次清空就自愈。
- 官方文档也写了：thumb 会在清空时被正确删除，即使原文件早就没了。

> 来源：Immich v1.82 Trash Feature 发布说明、`server/src/services/trash.service.ts` / `asset.service.ts` 实现分析

### 2. freedesktop.org Trash Specification 1.0（Linux 回收站事实标准）

- 目录结构 `$trash/files/`（实体）+ `$trash/info/*.trashinfo`（原路径 + 删除时间）。
- 铁律三条：
  1. **info 文件必须先写、且原子写**，再搬文件（`O_EXCL`）；
  2. `files/` 下的文件名**永远不能**用来反推原路径，只有 info 算数；
  3. info 缺失 = **紧急状态，必须显式告知用户**，不能静默当成普通文件。
- 我们的实现正好相反：清单**在搬完之后**写，清单缺失时 UI 直接显示「回收站是空的」——违反第 1、3 条。

> 来源：`specifications.freedesktop.org/trash/1.0`

### 3. 对照表

| 关注点 | Immich | XDG 规范 | 我们（现状） |
|---|---|---|---|
| 回收站真源 | DB 行（status=trashed） | info 文件 | 磁盘目录 + manifest，**索引不参与** |
| 删除时索引 | 改状态，不删 | 不涉及 | **立刻删行**（不可逆，失败就断） |
| 清空动作 | 删行 + 级联删文件/缩略图 | 删 files + info | **只删目录** |
| 幂等性 | 天然幂等 | 幂等 | 不幂等（删完就忘） |
| 元数据写序 | 先落库再动文件 | **info 先写** | **文件先动，清单后写** |
| 缩略图 | 随行级联删除 | 不涉及 | **永不删（IDB 泄漏）** |

## 五、修复方案

### 方案 A（最小修复，1 天，先止血）

1. `trash.js remove()`：删索引后补 `VRDB.deleteThumbs(['t:'+rel])`（缩略图 IDB 一起清）。
2. `trash.js empty()` / `purge()`：末尾加一次**兜底清扫** —— 遍历 `_回收站` 里已不存在的 batch，把清单里列出的 relPath 从 `file`/`thumb` 两表强制删除。删空之后再检查一遍，**幂等**。
3. `remove()` 改成「清单先写（占位）→ 搬文件 → 更新清单 → 删索引」；任一步失败，把已搬的文件搬回去并报错（补偿回滚），不再留半状态。
4. `indexer.build()`：对 `mode:'downloads'` / `'snapshot'` 的结果做**磁盘复检**（FSA `getFileHandle` 真实探一次），`d.exists` 只当提示不当判据。
5. `dwEmpty` / `trPurgePicked` 结束后补一次 `load()`，别只刷回收站抽屉。

> 保留 ADR-033 的磁盘回收站（换浏览器也能恢复，这点比 Immich 强），只是把「谁负责删索引」写清楚。

### 方案 B（推荐，2–3 天：把回收站做成状态，而不是目录）

按 Immich 的口径改造，但保留磁盘实体：

1. 索引加状态：`state: 'trashed' | 'ok'`，加 `trashBatch`、`trashedAt`；所有列表查询默认过滤 `trashed`。
2. 「删除」= 搬文件 + 行改 `trashed`（**不删行**）；「恢复」= 搬回 + 行改 `ok`；「彻底删除/清空」= 删磁盘文件（最后一个引用才删）+ `deleteThumbs` + `deleteFiles`，三件事一个函数做完，失败可重试。
3. 回收站列表改为**读索引**（`state==='trashed'`），`_manifest.json` 只作跨浏览器恢复的备份（读不到清单时按索引兜底 → 对应 XDG 第 3 条「紧急状态要显式提示」）。
4. 启动/扫描时跑一次 **sweep**：`trashed` 且磁盘无实体 → 直接清行清缩略图；`ok` 且磁盘无实体 → 标 `missing`（沿用 ADR-030），不静默删。
5. 顺带修掉前缀重复索引：扫描/对账时按 `absPath` 归并同一条目，一条物理文件只允许一条索引。

### 我建议

**先 A 止血（今天就能验），再按 B 重构（下个批次）。** 理由是 A 全是局部改动、能立刻让「死卡 + 缩略图泄漏」消失；B 会动 `B-44/B-45/B-52` 刚稳定下来的扫描侧，需要单独一轮回归。

不删任何文件，只修索引（`VRTrash.sweep()` 在打开资源库 2.5s 后自动跑一次，需已授权目录）：
