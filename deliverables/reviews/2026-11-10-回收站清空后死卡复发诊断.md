## 一、现象

苏哥报：「删除到回收站，清空了，然后索引还有出现」。

截图显示**主页**（不是回收站抽屉）按平台分组：yidianzixun 2 项、抖音 18 项、微博 8 项，其中大批卡片挂着红色「文件缺失」角标、缩略图是占位图。
「文件缺失」角标只由 `f.state === 'missing'` 绘制（`app.js:528`）——所以用户看到的是**文件已经没了、索引行还赖在主页**的死卡。

## 二、现场取证（只读，真实库）

| 证据 | 结果 |
|---|---|
| 索引状态 | 72 行 = 64 `ok` + 8 `missing`；`isRef`/`refOf`/无前缀行均为 0 |
| 逐条探盘 | **24 行「索引在、磁盘文件不在」**：16 条是刚删的「20261109_舞蹈少女」批（`state=ok`、`absPath` 完整、有 `sha256`、无 `downloadId`），8 条是 `D:/fake/*` 测试夹具 |
| 回收站 | `VRTrash.status()` = 0 项 / 0 批；磁盘 `_回收站/` 0 个文件 |
| 操作日志 | `_migration/ops-20261110-003604-kvd6.json`：`delete` moved=16、failed=0、batch `20261110-003602-tw05`<br>`_migration/ops-20261110-003608-1kzu.json`：`empty` items=16、ghosts=0、batches=8 |
| 快照 | `_library/index.json` 写于 00:35（删除前），含 30 条「舞蹈少女」；删除在 00:36:04、清空在 00:36:08 |

**结论 A**：清空那一步确实执行了，且声称处理了 16 条；但清完之后这 16 条仍完整躺在索引里（连指纹都在）。

## 三、排除法实验（关键）

### 3.1 扫描会不会把已删条目写回来？—— 不会

把 24 条死卡删掉（索引 72→48），重新开页等 9 秒（boot + sweep + 所有异步任务），再逐个跑
`VRIndex.build({mode:'downloads' | 'snapshot' | 'full' | 'reconcile'})`：

```
reload 之后      : n=48, back=0
build(downloads) : n=48, back=0   (total=1)
build(snapshot)  : n=50, back=0   (total=49，新增 2 条磁盘上真实存在但没索引的文件)
build(full)      : n=50, back=0
build(reconcile) : n=50, back=0
```

**结论 B**：当前代码下，开页与四种扫描都**不会复活**已删条目。ADR-074 里堵的那几条通道仍然有效。

### 3.2 引擎本身能不能删干净？—— 单批次/多批次都能，重复删除有洞

在真实库 `_selftest/` 造 3 个探针文件 + 索引行（不动任何用户素材），跑完整链路：

| 场景 | 结果 |
|---|---|
| 单批次 `remove(3) → empty()` | `purged=3`，索引 0 残留 ✅ |
| 拆成 3 个历史批次再 `empty()` | `purged=3`，索引 0 残留 ✅ |
| **同一条目删两次** | 第二次 `remove()` 见「原位置已没文件」，走「只删索引行」分支 → 回收站里留下**没有清单主人的孤儿副本**；随后 `empty()` 报 `purged=0` 却悄悄删了一整个批次目录 ❌ |

## 四、根因（诚实口径）

按 D1 铁律：**现有日志只记条数、不记核验结果，无法从历史记录反推当时具体是哪一步失败**，这一点标 REVIEW，不编故事。但代码层面三条缺口是确定的，且任何一条都能造出用户看到的现象：

1. **静默失效**：`purgeOne()` 里 `VRDB.deleteFiles([rel])` 被 `try/catch` 吞掉异常；`empty()` 的 `purged` 只数循环次数、**从不读库核对**。一旦 IDB 事务抖动或多页面并发写，就是「文件删了、索引行还在」，而 ops 日志照样写 `items: 16`。这是苏哥最忌讳的「配置看着对、实际没生效」。
2. **清理集合太窄**：`empty()` 只按 `trashedRows()` 取行。磁盘清单（`_manifest.json`，ADR-033 的跨浏览器备份）里的孤儿条目、以及状态被改回 `ok` / `missing` 的行，一概不管。
3. **没有清空后对账**：历史死卡（文件已不在磁盘、索引却还活着）会一直挂在主页，用户一清空就看见满屏「文件缺失」，主观上就是「删了又回来了」。

## 五、修复（只改 `js/library/trash.js` + 回归脚本，最小改动）

| # | 改动 | 作用 |
|---|---|---|
| 1 | `empty()` 清理集合 = `trashedRows()` ∪ 所有磁盘批次 manifest 的 `relPath`；统一批量重删后**读库核验**，返回 `verified` / `leftover`，删不掉时 `console.warn` | 杜绝「报成功、实际没删」 |
| 2 | `purgeOne()` 删行后读回验证，仍在则再删一次 | 单条「彻底删除」也不静默留行 |
| 3 | 新增 `dropDeadCards()`：文件**明确不存在**（只认 `NotFoundError` / `TypeMismatchError`，权限抖动不动）、回收站清单里没有、且非 `pendingArchive` / `isRef` / `trashed` 的行 → 删行 + 删缩略图；分批并发探盘，大库不卡首屏 | 清空后清掉所有死卡 |
| 4 | `empty()` 用 `includeMissing:true`（用户显式清空，语义即清干净）；`sweep()` 用 `false`，**绝不碰 `missing`**（守住 ADR-030） | 显式动作激进、自动自愈保守 |
| 5 | `remove()` 遇到「原位置没文件」且该行已在回收站 → 改走 `purgeOne()` 彻底删除 | 修掉重复删除留下的孤儿副本 |
