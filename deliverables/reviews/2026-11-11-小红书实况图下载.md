# 小红书实况图（live photo）：下载 + 库内分类/预览 + 动图现状（B-71）

> 2026-11-11 · 苏哥发来一条 5 张全实况的笔记，问「live 动图功能我们还没做吧？」
> 答：确实没做，而且**我们只下了静态首帧**——用户拿到一张不会动的 jpg。

---

## 一、什么是小红书的实况图

一张实况 = **静态 JPEG（首帧）+ 2~3 秒 mp4**。用户要的是「能动的那份」。

数据结构（SSR state，实测 `imageList[i]`）：

```js
{
  livePhoto: true,
  urlDefault: "http://sns-webpic-qc.xhscdn.com/.../1040g3r832791u6d06q8g5...!nd_dft_wlteh_webp_3",
  stream: {
    EF4: [{ masterUrl: "https://sns-video-v3.xhscdn.com/stream/1/10/19/xxx_19.mp4?sign=…",
            backupUrls: ["https://sns-bak-v1.xhscdn.com/…", "https://sns-bak-v6.xhscdn.com/…"],
            qualityType: "HD" }],
    EF5: [], EF6: [], EF7: []
  }
}
```

## 二、两个必须解决的对接问题

**① 怎么把「扫描到的这张图」和「state 里的这条实况」对上**

侧边栏是按 DOM 扫图的，顺序、去重、过滤都可能变；按 index 对齐迟早错位。
实测发现 DOM 里 `<img>` 的 pathname 尾段与 `state.imageList[i].urlDefault` 尾段**完全一致**
（`1040g3r832791u6d06q805nrr3iag99ub333keug`）。所以按「素材 id」匹配：

```js
key = new URL(u).pathname.split('/').pop().replace(/![a-z0-9_]+$/i, '').toLowerCase()
```

**② 实况 mp4 走图片下载队列**（不另开视频通道）

一行队列里静态图后面跟一条 `_live.mp4`，去重/进度/失败统计天然覆盖。
但这会踩到 `vrImgExt` 的白名单：`VR_IMG_EXT_OK` 只有图片扩展，
`mp4` 会被**强改成 jpg** —— 实测文件头是 `ftypisom`（真 mp4）、后缀 `.jpg`，播放器和库全认错。

## 三、实现

| 位置 | 改动 |
|---|---|
| `js/background.js` | 新增 `vrXhsLiveProbe`（读说明：取 noteId → note.imageList → 只要 `livePhoto` 且 `stream.EF4` 有 `masterUrl`）；新增消息 `vrXhsLive` |
| `js/background.js` | `vrImgExt`：URL 明确以 `.mp4` 结尾时保留 `mp4`（只放行 mp4，不开别的口子） |
| `js/image-page.js` | 扫描后 `attachXhsLive()` 按素材 id 挂 `it.live / it.liveBackup` |
| `js/image-page.js` | 卡片左上角「实况」金色角标；批量下载时静态图后追加 `_live` 条目；大图预览「下载这张」也带实况 |
| `css/image-page.css` | `.ip-live` 角标样式（左上，金色描边，与右上的「已下载/可换原图」错开） |

**踩坑**：`vrXhsLive` 的消息处理最初用了 `sender.tab.id`。但调用方是扩展页（侧边栏自己就是
一个 tab），`sender.tab` 指的是**侧边栏自己**，probe 注入到扩展页上 → rows 恒为空。
必须用消息里显式传的 `tabId`。

## 五、没做的（说清楚）

1. **库里不播实况**：资源库把 jpg 和 mp4 当两条素材（照片 + 短视频），
   没有「点开照片播实况」的一体化预览。要做需要在库里做配对（按文件名 `_live` 后缀关联）。
2. **不合成动态 WebP/视频**：只给原始两件套，不替用户转格式。
3. **其它平台的实况**（微博 live、Instagram）没做，本次只覆盖小红书。

## 七、附：苏哥追问「其他平台 gif 动图」和「筛选图片时支持 live 吗」

### 7.1 动图（gif/apng）现状

| 能力 | 状态 |
|---|---|
| 下载 | ✅ 支持。`VR_IMG_EXT_OK` / `IMAGE_EXT` 都含 `gif`、`apng`，图床的 GIF 原样落盘（不转码、不丢帧） |
| 库内分类 | ✅ 归 `anim`（动图），有独立页签和计数；**webp 不算动图**（小红书/IG 大量静态 webp，2026-11-06 用户纠正过） |
| 预览 | ✅ 逐帧播放器（`VRAnim`，原生 ImageDecoder，可暂停/逐帧/循环/倍速），不支持时优雅退回静态图 |
| 平台范围 | 通用：只要站点把 gif/apng 当图片资源给出来，所有站都能下。小红书把 GIF 当 `type=video`（其实是动图），会归视频——这是站点定义，不是我们丢帧 |

结论：**gif/apng 动图全链路早就通**，没有平台限制。

### 7.2 实况（live photo）在库里的筛选

本轮（B-71 下半）补上「库内实况分类」，与图片/动图/视频并列：

- **类型页签**新增「实况」，计数单独统计
- 判定：一张照片 + 同目录同前缀 `xxx_live.mp4` **成对出现**才归「实况」；只有照片、或只有视频，都不算（不挂空角标、不破预览）
- **卡片右上角金色「实况」角标**
- **预览**：照片打底，实况视频静音循环浮在正中，点一下开声音（手机相册那套交互）
- 纯逻辑单测 `tools/test-live-pair.js` **17/17**（配对 / 缺项 / 大小写 / 动图归类）

> 说明：实况照片和它的 mp4 仍是**两条独立条目**（一张 image + 一条 video），
> 只是 UI 把「照片那条」标成实况、筛选时能单独选出来。不合并条目——
> 用户可能只想要那张照片，删一条不该牵连另一条。

### 7.3 还没做的

1. 其它平台实况（微博 live、Instagram）——本次只覆盖小红书；
2. 库里「点照片自动带出并播放实况」之外，没有做「把照片+实况打包成一个文件」的导出；
3. 侧边栏「实况」没有独立筛选档（它混在图片里、靠左上角金色角标识别），要单独筛得去资源库的「实况」页签。
