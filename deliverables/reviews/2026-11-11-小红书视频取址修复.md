# 小红书视频「下错」：取址链路的通用性缺陷（B-70）

> 2026-11-11 · 苏哥报「小红书下载的视频不是我点击那个页面的，怀疑是通用问题」
> 结论：**确实是通用问题**。取址靠「整个 tab 的嗅探池 + 按分辨率排序」，SPA 站必错。

---

## 一、症状与取证

用户点开笔记 A → 点下载 → 落盘的是笔记 B 的视频（往往是之前逛过、分辨率更高的那条）。

真机取证（Edge 157 隔离实例，小红书笔记页）：

| 观测 | 结果 | 说明 |
|---|---|---|
| 笔记页 `<video>` 的 `currentSrc` | `blob:https://www.xiaohongshu.com/…` | **MSE 播放**，拿不到真实地址 → 「正在播放」探测形同虚设 |
| 嗅探缓存 `cacheData[tabId]` | 按 **tabId** 累积 | 小红书切笔记是 SPA（不换 tab、不触发 `loading`）→ 缓存里同时躺着多篇笔记的视频 |
| 通用排序 | 分辨率 → 体积 → 正在播放 | 「正在播放」只当平手时的加权 → **别的笔记更高清就赢了** |
| 媒体库记录 | `pageUrl` 存的是带 `xsec_token` 的一次性地址 | 同一篇笔记每次都不同，溯源键不稳定 |

四条叠加，就是「点的 A、下的 B」。而且**与站点无关**：微博信息流、YouTube、B 站单页、任何 SPA 都走同一条通用链路。

## 二、修法（四层，前三层通用）

**① 小红书专用取址（不再依赖嗅探）**

从页面 SSR state 直接取「这篇笔记自己的」视频流：

```
window.__INITIAL_STATE__.note.noteDetailMap[<noteId>].note.video.media.stream
  = { EF4: [...], EF5: [...] }
    EF4 → 完整 mp4（.mp4）
    EF5 → fmp4 分片（.m4s，单独下一个只有几秒）
```

- 只给**完整 mp4** 当选项（没有完整文件才退回分片并标注「需合并」）
- 标签按短边显示（竖屏 1080×1920 叫 1080p，不叫 1920p）
- 作者/标题/noteId 与选项同一次注入取回（避免「隔几秒再抠一次抠到另一条」——抖音踩过）

**② 通用：候选池按「当前文档」过滤**

新增 `VRVideoQuality.docKey(url)` = `origin(去 www) + pathname + 内容 id 类参数`。
`vrVideoOptions` 只保留 `webUrl` 与当前文档同键的嗅探记录 —— 逛过 A、B 两篇后，A 的记录不会再参与 B 的选源。
签名/token/utm 一律丢弃（否则同一篇笔记每次进都不同键，会把当前页的记录也误杀）。

**③ 通用：两段式排序**

新增 `VRVideoQuality.prioritizePlaying(list, playing)`：

1. 先用「正在播放」锁定**是哪个作品**（用 `familyKey` 抹平 CDN 节点差异：sns-video-ak/bd、p3/p9-pc-sign、wx1~wx4）；
2. 再在该作品的所有码率里取最高。

老实现是「全页按分辨率排第一」，多视频页面必然下错；而单纯把 playing 置顶又会退回微博 720p 的老毛病 —— 两段式两者都不牺牲。

**④ 溯源地址归一**

`trace.pageUrl` 改为 meta 优先（`explore/<noteId>` / `video/<awemeId>`），不再把 `xsec_token` / `modal_id` 写进库。

## 三、验证

真机（小红书，两条不同笔记各下一次，取最低档省流量）：

| 笔记 | 作者 / 标题 | 落盘文件 | 库 `pageUrl` |
|---|---|---|---|
| 6af2f64d… | 健身小阿姨 / 人一旦染上游泳🏊 | `小红书/健身小阿姨(@668fb…)/…_人一旦染上游泳.mp4`（16.9MB，720p 完整） | `https://www.xiaohongshu.com/explore/6af2f64d000000002b01a0b6` |
| 6ae5e4fd… | 查理宝宝慢点长大 / 带娃松弛… | `小红书/查理宝宝慢点长大(@5c05…)/…_带娃松弛….mp4` | `https://www.xiaohongshu.com/explore/6ae5e4fd0000000025013c39` |

两条互不串；options 都是 1080p/720p 完整 mp4（无 m4s 分片）；URL hash 前缀与 noteId 一一对应（`01eaf2f64c…` ↔ `6af2f64d`）。

单测 `tools/test-video-quality.js` **100/100**：新增
- J 段：同族取最高 / 正在播放压过更高清的别的视频 / blob 兜底
- K 段：小红书换 token 同键、YouTube `v=` 区分、微博同页同键、`www` 归一

隔离 e2e **6/9**：`stage-rewrite` 18/21、`skin` 15/20 失败断言全在**资源库 UI / 安装页**（`#pvFilm`、`#setdrawer`、安装页配色），属并行会话未完成的改动，与取址无关；`e2e-buttons` 按规则需隔离库单独跑。

## 四、遗留

1. **微博信息流 / YouTube 单页**：通用两层（文档过滤 + 两段式）已覆盖，但没有真实素材回归，下轮实测时确认。
2. **m4s 分片合并**：目前「只给完整 mp4」，所以 4K 档（只有分片）拿不到。要支持得先把分片拼成 fMP4 —— 单独立项。
3. 库里已有的历史记录（如「公众号排版 第6期」，`pageUrl` 指向已 404 的笔记）无法自动判定对错，需要用户按「来源」链接自行核对；修复后新下载的都是归一地址。

## 五、测试产物清理
