- 日期：2026-11-12
- 触发：苏哥报「微博最高清不是 4K，默认最高就是 1080，应该以探测到的最高清为准，需要低清晰度自己选」

## 一、结论先说

微博这条链路**三个 bug 叠在一起，导致「补高清」从上线起就没成功过**，用户看到的上限永远等于浏览器实际请求过的那一档。

修完后实测（苏哥给的 t.cn 短链 → `video.weibo.com/show?fid=1034:5364493765771302`，央视新闻）：

| 档位 | 体积 | 说明 |
|---|---|---|
| **2160p（4K）** | 161.4 MB | **默认选中，标「最高清」** |
| 1440p（2K） | 78.2 MB | 可选 |
| 1080p | 51.1 MB | 可选 |
| 720p | 27.1 MB | 可选 |
| 480p | 13.7 MB | 可选 |

## 二、三个 bug（都不是「字段没覆盖」这么简单）

### BUG-1　解析跑在页面主世界，模块却只装在后台

`vrWeiboHdProbe` 用 `chrome.scripting.executeScript({world:'MAIN'})` 注入页面取数据，
但函数里第一行是：

```js
const Q = self.VRVideoQuality;
if (!Q) { return null; }
```

`VRVideoQuality` 是后台 SW 通过 `importScripts` 装的，**页面主世界没有**。
于是这两行恒为真分支 → 探针**永远返回 null**，补高清一次都没跑成。

> 这类「跨世界引用不存在的模块」不会报错，只会静默返回 null ——
> 属于最难发现的一类缺陷（跟 B-72 的「静默跳过」同源）。

**修法**：页面侧只负责「找 id + 取 JSON」，解析交回后台（`VRVideoQuality.weiboVariants`）。

### BUG-2　请求用的是视频文件 id，接口要的是微博正文 id

`ajax/statuses/show?id=` 需要**微博正文 id（status id）**，
而代码从视频 URL 里取的是 `media_id`（视频文件 id）。实测直接返回：

```json
{"ok":0,"message":"该微博不存在","error_code":20101}
```

**真 id 的可靠来源**（真机逐个验证过）：

| 来源 | 形态 | 适用 |
|---|---|---|
| 发布时间链接 | `<a href="//weibo.com/<uid>/<statusId>">` | `weibo.com/tv/show/...` |
| query 参数 | `?fid=1034:<id>`、`?mid=`、`?id=` | `video.weibo.com/show` |
| 卡片属性 | `[mid]` / `[data-mid]` | 信息流、详情页 |

**修法**：页面侧按「URL → query → DOM 属性 → 链接 → media_id 兜底」收集候选，
逐个试到 `ok===1` 且有 `playback_list` 为止（上限 4 次，控风控）。

### BUG-3　4K 只在 `playback_list` 里，固定字段最高 1080p

老实现按字段名挑一条：`mp4_1080p_url > mp4_hd_url > stream_url_hd > …`。
微博的 4K/2K 在 `page_info.media_info.playback_list[]` 里：

```json
{ "meta": { "label":"mp4_2160p", "quality_index":2160, "quality_label":"4K", "type":1 },
  "play_info": { "url":"…", "width":3840, "height":2160, "size":169283815, "bitrate":5411984 } }
```

**修法**：新增 `weiboVariants(detail)` 读全档位；老字段作为兜底（且**保持字段顺序不排序**，
因为 `hd.mp4` 会被 URL 解析成 720p，反把明确的 `mp4_1080p_url` 挤下去 —— 单测 E11 抓到过）。

### 附加根因（第 4 个，独立于上面三个）

`familyKey` 用「域名 + pathname」归族。微博各码率**文件名不同**：

```
…/o0/Q6u4jgLA…010.mp4?label=mp4_1080p&media_id=5342782311825499
…/u0/wIP3pR9z…080.mp4?label=mp4_2160p&media_id=5342782311825499
```

→ 4K 被当成「另一个视频」，`prioritizePlaying` 只会在 720p 那一族里取最高。
**修法**：微博按 `media_id` 归族（`weibocdn.com/video#media_id=…`）。

## 三、顺带修的两个显示/落盘问题

| 问题 | 真因 | 修法 |
|---|---|---|
| 竖屏视频显示成「1920p」 | 用 `height` 当档位，竖屏 1080×1920 的 height 是 1920 | 优先 `quality_index`，否则取**短边**（行业惯例） |
| 面板出现两个「1080p」 | 嗅探条目 `height` 为空，入池去重时读到 0 → 判不出重复 | 比较时用「有效高度」= `height || heightFromUrl(url)` |
| 落盘是 238 字节的 `.htm` | `downloads` 记录里 `mime` 常为空，`vrDownloadLooksInvalid` 只看 mime → 放过反爬页 | 补「后缀是 html/json/xml 即判坏」；判坏后自动降级到离屏直连（带 Referer），实测拿到 1135983 字节真视频 |

## 四、通用性检查（苏哥要求「其他网站也要默认最高清」）

四个档位产出点逐个查过，**全部是「能用的最高清在前」**：

| 分支 | 排序依据 | 结论 |
|---|---|---|
| 通用站点 | `sortCandidates`：分辨率 → 体积 → 当前播放（仅平手） | ✅ 最高清第 0 位 |
| 通用 + 正在播放 | `prioritizePlaying`：先锁作品，再族内取最高 | ✅ 不会被别的视频顶掉 |
| 小红书 | 完整 mp4 优先 → 像素 → 码率 | ✅ |
| B 站 | 一键下载优先 DASH（1080P）> 整段 MP4（720P） | ✅ |
| 抖音 | H.264 优先 → 像素面积 → 码率 | ✅（H.265 后置是有意的：Chromium 不带 HEVC 解码，下了播不了） |

`vrVideoDownload(tabId,'',true)`（一键下载）统一取 `options[0]`。
已有单测 B1~B8 锁住「最高清排第一 / 分辨率降序 / 已知优先于未知」。

> 真正缺的不是排序，是**主动补档**：目前只有微博会去站点接口问「还有没有更高档」。
> HLS 站点靠 master 展开（已覆盖大多数流媒体）；YouTube 有 `youtubei/v1/player` 专用探测。
> 直链 MP4 站点只能拿到页面请求过的档位 —— 这是浏览器模型决定的，不是排序问题。

## 五、回收站：右侧抽屉 → 居中弹窗

苏哥原话「右侧的很难用」。改前：440px 贴右边，长文件名换行，一屏五六条。

**只改 CSS**（`css/library.css` 的 `.drawer-mask` / `.drawer`），HTML 与 `app.js` 一行没动：

- 尺寸 760px（`min(760px, 92vw)`），最大高度 `82vh`
- 居中：`left:50%;top:50%;translate(-50%,-50%)`，缩放入场
- **关闭态必须 `visibility:hidden` + `pointer-events:none`** —— 原来是靠 `translateX(100%)` 推出屏幕，
  居中后没有「屏幕外」可躲，只设 `opacity:0` 会让透明层继续吃点击，库页点不动
- 保留 `.on` / `.show` 双类名兼容（历史坑：只认 `.on` 时点「回收站」毫无反应）

实测（1440×900）：760×339 居中（误差 <8px），开→可见，关→`visibility:hidden`；截图 `deliverables/assets/2026-11-12-trash-modal.png`。

## 七、未做 / 已知限制

1. **仅微博做「主动补档」**。其它直链 MP4 站点仍只能拿页面请求过的档位（浏览器模型限制）。
2. **抖音 H.265 档后置**：不是漏了，是 Chromium 解不了 HEVC；要支持得先转码。
3. **信息流场景未真机回归**（隔离实例无微博登录态）。探针支持 `[mid]` / `[data-mid]`，
   但真流里的 DOM 结构需登录后复核 —— 苏哥下次刷微博点一次即可确认。
