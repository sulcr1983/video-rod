# 「抓图」为什么完全不可用 —— 复盘与对标

> 日期：2026-11-12 ｜ 触发：苏哥截图（微博页 popup「图片 0」+ 弹窗「本页图片 2」两张裂图）
> 苏哥原话：「这个功能基本上不可用。你怎么做的？」「参考一下星愿浏览器的各个扩展，看看人家是怎么做的。」
> 关联：B-78（同一入口的上一轮修复，只修了图集通道，没修 popup 抓图）、B-79（本次）

## 一、结论先行

**不是「没做」，是「抄了一份，还把门槛抄反了」。**

popup 的「抓图」按钮背后，是一份**独立的、和侧栏不共享的**扫描函数
（`js/popup-videorod.js` 旧 `collectImagesInPage`）。它的尺寸门槛写的是：

```js
if (Math.min(dw, dh) < MIN_SHOW) { continue; }   // MIN_SHOW = 600
```

即「显示尺寸的**短边**必须 ≥ 600px」。而微博信息流里的图，页面上显示宽度普遍 **300~500px**
（缩略显示、点开才是大图），短边 200~400 —— **一张都过不了**。

于是整页只剩两个不遵守这个门槛的东西：一张 `1024×1024` 的广告位（`background-image` 通道进来的，
尺寸记 0 但不判门槛）和一张打不开的背景图。这就是截图里那「2 张裂图」的来源。

雪上加霜的是「图片 0」：popup 顶部那三个数字（视频/图片/流）
统计的是**网络嗅探条目**（`#mediaList .panel` 上由 `isPicture()` 打的 class），
而嗅探层按内容类型白名单收资源（`G.Type`），图片类型默认没启用 ——
那个数字从上线起对微博页恒为 0，与页面上到底有没有图无关。
（顺带发现设置里那个「图片嗅探」开关 `imgSniff` **全仓没有任何代码消费**，是纯 UI 摆设。
本轮不动：真接上会把整页图片塞进媒体列表，比现在更乱；正确做法是让「图片」这个入口直达抓图，
已记 `docs/BACKLOG.md` B-80。）

## 二、对标：人家是怎么做的

材料来源：`docs/COMPETITOR-EXTENSIONS.md`（直接读星愿 `Default/Extensions/` 源码）+
`docs/RESEARCH-COMPETITOR-IMAGE.md`（IDC / Image Harvest 源码 + README）。

### 2.1 图片发现：两家通用扩展都是「宽进」

| 能力 | 图片下载器 4.0.0（星愿里装过） | Image Downloader Continued | 我们修复前（popup 抓图） |
|---|---|---|---|
| `<img>` src | ✅ | ✅ | ✅ |
| `srcset` 取最大 | ✅ 逐个 `new Image()` 比面积 | ✅ | ❌ |
| `<picture><source>` | ❌ | ✅ | ❌ |
| **`data-src` 等懒加载属性** | ❌ | ✅ | ❌（只在候选里，url 仍用占位） |
| `background-image` | ✅ computed | ✅ | ✅（但不判门槛、不校验可达） |
| 源码/JSON 正则 | ✅ | ✅ | ❌ |
| **尺寸门槛** | **只挡 100×100 以下的图标** | 100×100 | **显示短边 ≥ 600** ← 翻车点 |
| 打不开的图 | 不校验 | 不校验 | 不校验（所以裂图进了列表） |

**最关键的一条**：人家判的是「**原始像素别太小**」（100×100，挡图标就够），
我们判的是「**显示尺寸够不够大**」——显示尺寸是站点 CSS 说了算的，
信息流/图墙天然把人家的原图缩到 300px 展示。**用显示尺寸当采集门槛，等于按站点的缩略图排版决定用户能不能存图。**

### 2.2 原图：人家专门为「拿最大那张」写了逻辑

- 图片下载器 4.0.0：`srcset` 里逐个 `new Image()` 预载、比面积取最大。
- IDC：`a[href]` → `srcset` 最大 → `data-*` → `data-ri` → `currentSrc`，五级候选；
  还有「去掉 URL 里 `resize` 类参数拿原图」。
- 我们的 `collectCandidates` 这五级都有，**但微博的清晰度不在 query 参数里，在路径段**
  （`/thumb150/` `/mw690/` `/large/`），所以「去 resize 参数」对微博完全无效 ——
  修前存下来的是 690px 压缩图，用户以为存到了原图。

### 2.3 下载：两家都弱，我们更强（这条不用抄）

图片下载器 4.0.0 只有 `chrome.downloads.download` 单发，防盗链直接 403；
Image Harvest 是 fetch blob + JSZip 打包。我们的 `vrImgResolve` 是
「候选逐个 fetch 校验 content-type，全失败回退最后一个」，在这个问题上比两家都稳。

### 2.4 入口形态：两家都不在页面上放常驻浮标

点击图标 → popup / 侧栏清单。这与我们现在的形态一致，不动。

## 三、改了什么（四条，最小改动）

| # | 改动 | 落点 | 为什么 |
|---|---|---|---|
| 1 | **popup 抓图不再自己抄扫描器**，直接复用页面已注入的 `VRImageUtil`（= 侧栏清单/悬停同一个模块），三条通道 + 同一套口径；模块没注入时先补注入一次 | `js/popup-videorod.js` `collectImagesInPage` | 一份逻辑两处实现，必然漂移；这次漂移的代价就是「完全不可用」。改完「侧栏几张 = 弹窗几张」 |
| 2 | **采集门槛回到「原始像素 ≥ 100」**，显示尺寸只用来挡图标（48px），不参与「收不收」 | 同上（传 `minSize: imgMinSize`、`minShow: PANEL_MIN_SHOW`） | 这是人家两家共同的做法。显示尺寸当门槛 = 按站点排版决定能不能存图 |
| 3 | **微博原图升级**：`/thumb150/` `/bmiddle/` `/mw690/` → `/large/`，且必须是候选**首位**（后台按顺序试，排末尾等于没有）；拿不到自动退下一个 | `js/lib-image-util.js` `upgradeSinaimg` + `collectCandidates` ⑦ | 修前存的是 690px 压缩图。回调里 `vrImgResolve` 会 fetch 校验，所以 `/large/` 不存在也不会失败 |
| 4 | **裂图不再进列表**：`fillSizes` 预载时把加载失败的地址标 `fail`，扫描结果里剔掉并提示剔了几张；占位 src（1x1/blank.gif）自动回退到 `data-src` | `fillSizes`、`scanImages` `pickUrl`、弹窗渲染 | 截图里那两张灰裂图就是「不校验可达性」放进来的。用户看到裂图会直接判「这功能坏了」 |

顺带：弹窗里「尺寸未知」不再一律写「背景图」（源码通道抓到的图也被标成背景，误导），
改为「背景图 · 尺寸未知」/「尺寸未知」。

## 五、明确不做

| 不做 | 为什么 |
|---|---|
| 抄「每张图挂悬浮下载钮」（图片下载器 4.0.0 / IDC 的做法） | 长页面上会糊满屏幕；我们走清单，且用户已有悬停取图入口 |
| 抄 JSZip 打包下载 | 与本轮缺陷无关，且要改整条落盘链路；独立立项 |
| 抄 iframe 递归 | `all_frames:false` 是既有边界（B-29），牵涉消息路由，不顺手塞进来 |
| 修「图片 0」那个恒为 0 的计数 | 是独立缺陷（另一个类型统计口径），本轮只记录不混入。已记 `docs/BACKLOG.md` B-80 |
