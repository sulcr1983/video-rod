# 图片批量失败审计（2026-11-13）

> 触发：苏哥反馈「图片下载（尤其是批量下载和批量嗅探）一直失败；除了单图，其他都不太行」。
> 范围：`js/lib-image-util.js`、`js/image-*.js`、`js/popup-videorod.js`、`js/background.js` 的图片段、`js/library/save.js`、`manifest.json`、图片相关测试与门禁。
> 方法：逐行读代码 + 读星愿浏览器实际安装的 **ImageAssistant 1.70.7** 源码（`odphnbhiddhdpoccbialllejaajemdio`）。本文只写能复核的事实；未实测的明确标「未定性」。
> 结论：不是单点 bug，而是**四条链路各自实现扫描/下载**，唯一做对的「候选逐个校验」只存在于悬停单张；批量入口绕过它，同时落盘、命名、去重、测试门禁四层有缺口。

---

## 一、一句话因果链

```
批量入口把 bestCandidate 当唯一 URL
  → 后台 vrImgDownload 不消费 candidates（首选 404/403 就整张失败）
  → 快速失败只等 2.5s 且不校验内容（失败被当成功）
  → 落盘可能静默回退浏览器下载目录（用户找不到）
  → 命名/扩展名错 + 幽灵记录跳过（用户看到“下过了”但盘上没有）
  → 批量每张全表查重 + 全量哈希（大批量超时/中断）
  → 测试门禁不含批量落盘套件（问题长期不被发现）
```

## 二、P0：批量下载正确性

### D-01 批量不消费候选链（头号原因）

- **现象**：单张悬停能下；侧栏「本页图片」、popup「抓图」、资源库面板、「全部 N」批量大量失败。
- **证据**：
  - 单张：先 `vrImg.resolve` 逐个 fetch 校验 content-type，再下载（`js/image-hover.js:837-843`）。
  - 批量：三处都把 `bestCandidate()` 的结果当唯一 URL（`js/image-batch.js:398`、`js/image-page.js:945`、`js/image-panel.js:624`）。
  - 后台：`vrImgDownload` 只读 `msg.url`（`js/background.js:1110-1118`）；`vrImgBatch` 传了 `candidates`（`js/background.js:1414-1432`）但函数不消费。
- **影响**：微博 `/large/` 对老图/长图/动图 404、X `?name=orig` 404、srcset 最大图 404、防盗链 403 时，批量整张失败；单张会自动退下一个候选。
- **修复归属**：阶段二 P-01。

### D-02 查重跳过不校验文件存活

- **证据**：`vrImgDownload` 下载前 `vrFindExistingMedia` 命中即 `skipped`（`js/background.js:1126-1131`）；该函数只跳过 `state==='missing'`，不校验文件是否存在、大小是否 > 0（`js/background.js:4781-4810`）。
- **对比**：视频/微博批量 `vrBulkSaveItem` 有 `vrEntryFileAlive` 显式校验并删除死条目（`js/background.js:4697-4709`）。
- **影响**：库内 0 字节、HTML 反爬页、FSA 权限失效的旧条目会让整批「全部跳过」，用户磁盘上没有文件。
- **修复归属**：阶段四 S-02、阶段二 P-04。

### D-03 快速失败窗口过短、失败被当成功

- **证据**：`vrWaitDownload(downloadId, 2500)`（`js/background.js:1248`）；超时返回 `null`，`vrImgDownload` 继续返回 `{ok:true}`（`:1280-1283`）。
- **影响**：批量并发时 403/中断常晚于 2.5 秒；计数成功，文件实际是 0 字节/半截；DNR 规则要等 30 秒兜底才撤。
- **对比**：`vrBulkSaveItem` 等 4 秒且区分大文件仍在下载（`js/background.js:4728-4735`）。
- **修复归属**：阶段二 P-02。

### D-04 落盘不校验内容类型/图片头

- **证据**：
  - FSA 直写 `pumpUrl` 只判 `r.ok`，不判 content-type（`js/library/save.js:382-410`）。
  - `vrDownloadLooksInvalid` 只用于视频/其他路径（`js/background.js:3780-3796`；调用点 4046/6471/6767），图片批量未用。
- **影响**：200 + HTML 反爬页、0 字节、半截文件会被计成功并入库。
- **修复归属**：阶段二 P-03、阶段四 S-03。

### D-05 popup 批量保存没有队列，且先记“已下载”

- **证据**：`downloadPickedImages` 逐条 `chrome.runtime.sendMessage` 同时发（`js/popup-videorod.js:2420-2444`）；发送前 `markDownloaded(filename)`（`:2422-2423`），失败只 `console.warn`（`:2439-2441`）；随后立即 `tip('已保存 N 张')`（`:2447`）。
- **影响**：无并发池（微博 3 并发已不稳，见 `js/image-batch.js:26-28`）；失败不回滚；提示“已保存”时可能一张都没落盘；下次被 `isDownloaded` 跳过，永久不下。
- **修复归属**：阶段三 E-02、阶段二 P-05。

### D-06 命名与扩展名错误

- **证据**：
  - popup 的 title 已含扩展名（`buildNameFromInfo` 自动补，`js/naming.js:585-589`），后台再拼一次 → `xxx.jpg.jpg`（`js/background.js:1158-1161`）。
  - 面板批量所有 `title` 都是同一个 `pageTitle`，无序号（`js/image-panel.js:615-627`）；FSA `freeName` 异步探测（`js/library/save.js:330-350`），并发同名会覆盖或得到不确定 `_01`。
  - 无扩展名 CDN（小红书/抖音）按 URL 猜 `.jpg`，实际可能是 webp/avif（`js/background.js:925-938`）。
- **影响**：文件名不可读/打不开/数量对不上。
- **修复归属**：阶段四 S-04、阶段三 E-03。

### D-07 面板批量把失败标成成功

- **证据**：`runQueue` 的 `settle` 恒返回 `ok:true`（`js/image-batch.js:455-467`）；`downloadSelected` 以 `res.ok` 给卡片加 `done`（`js/image-panel.js:639-645`）。
- **影响**：失败项在 UI 上消失，用户无法重试。
- **修复归属**：阶段二 P-05、阶段三 E-03。

### D-08 大批量性能与生命周期

- **证据**：每张图 `vrFindExistingMedia` 全表 `getAllFiles()`（`js/background.js:4790`）+ `vrImgContentDedupe` 全量/采样哈希（`:4853-4909`）+ 入库。超时线：回执 120s（`js/image-batch.js:561`）、无进度 60s（`:31`）、回执丢失 25s（`:497`）、MV3 单事件约 5 分钟。
- **影响**：200 张必中断，报「批量下载中断（扩展后台休眠）」。
- **修复归属**：阶段二 P-06、阶段四 S-05。

### D-09 ZIP 打包绕过后台

- **证据**：`packZip` 在扩展页直接 `fetch`（`js/image-page.js:1084-1092, 1133-1135`），不带 Referer、不走 DNR、不逐个候选回退。
- **影响**：防盗链站点整批失败，用户把“批量打包”当批量下载。
- **修复归属**：阶段二 P-07。

### D-10 确认条数字与实际下载口径不一致

- **证据**：`countNow` 用 `scanImages({minWidth:100,minHeight:100})`，`minShow` 落默认 500（`js/image-batch.js:245-256`）；`collectItems` 显式传 `minShow:48`（`:371-387`）。
- **影响**：按钮/确认条说 N 张，实际下载更多或更少。
- **修复归属**：阶段三 E-04。

## 三、P0/P1：批量嗅探覆盖

### S-01 只扫主 frame

- **证据**：图片内容脚本组 `all_frames:false`（`manifest.json:211`）；`chrome.scripting.executeScript` 均未传 `allFrames`（`js/image-page.js:163-183`、`js/popup-videorod.js:2182-2199`、`js/background.js:1583-1587`）。
- **影响**：iframe 内的图全漏。ImageAssistant 用 `all_frames:true` + `webNavigation.getAllFrames` 逐 frame 注入。

### S-02 不扫 Shadow DOM

- **证据**：`scanImages` 只 `doc.querySelectorAll('img')`（`js/lib-image-util.js:766`）；`scanBackgrounds` 也只查主文档（`:701`）。
- **影响**：组件库/图墙/Reddit 类页面漏图。

### S-03 网络层图片候选完全没接

- **证据**：`G.Type` 默认白名单不含 `image/*`（`js/init.js:63-73`）；`net-sniff.js` 的 `MEDIA_RE` 只有视频/音频，图片只特判小红书（`js/net-sniff.js:38-56`）；`imgSniff` 无消费方（`js/popup-videorod.js:26,276,326`）。
- **影响**：滚过去的图、JS 加载后从 DOM 移除的图、懒加载前就请求过的图、外部 CSS 背景图都拿不到。这是与 ImageAssistant 最大的能力差距。

### S-04 源码/JSON 通道被降级

- **证据**：侧栏/popup 只在「DOM+背景都为空」时跑源码通道（`js/image-page.js:223`、`js/popup-videorod.js:2243`）；图集却无条件跑（`js/image-album.js:105-111`）。
- **影响**：JSON 型页面只要 DOM 有一张小图，源码里的大图全漏；三入口口径不一致。

### S-05 显示尺寸 80px 当采集门槛

- **证据**：`LIST_MIN_SHORT=80`（`js/lib-image-util.js:45`），`scanImages` 用它做 `minShort`（`:811-815`）。
- **影响**：图墙缩略图显示 40~79px（原图很大）被静默丢弃。与竞品「只挡 100×100 原图，显示尺寸只用于排序/过滤图标」相反。

### S-06 未解码/已解码口径不一致

- **证据**：`sized=false` 时不判 `minShow/minShort`（`js/lib-image-util.js:806-815`）；`fillSizes` 回填后侧栏不二次过滤（`js/image-page.js:269-287`），popup 只按原图像素过滤（`js/popup-videorod.js:2275-2279`）。
- **影响**：头像/图标（原图大、显示小）在慢加载时时序性混入，快加载时被挡；每次扫描数量不稳定。

### S-07 尺寸回填覆盖不足

- **证据**：`fillSizes` 限前 60 张 / 2.5 秒总预算（`js/lib-image-util.js:645-686`）；资源库面板完全没接（`js/image-panel.js` 无调用）。
- **影响**：大页面后续图永远「尺寸未知」；面板无法按档位筛。

### S-08 扫描是一次性快照

- **证据**：侧栏只在 `init/scan` 时扫（`js/image-page.js:1392-1414`），只有面板打开时有 MutationObserver（`js/image-panel.js:1028`）。
- **影响**：SPA 切笔记/无限滚动后列表过期，必须手动 ⟳。

### S-09 大页面扫描性能

- **证据**：`scanImages` 对每个 `<img>` 调 `getBoundingClientRect`（`js/lib-image-util.js:550-573`）；`scanBackgrounds` 对 `div,section,article,a,span,figure,li,td,header` 全量 `getComputedStyle`（`:699-733`）。
- **影响**：几千节点页面卡主线程，用户以为“扫描失败”。

### S-10 侧栏 tabId 解析不可靠

- **证据**：`resolveTab` 假设 `chrome.tabs.query({currentWindow:true})` 按最近使用排序（`js/image-page.js:105-135`）；Chrome 不保证。
- **影响**：点图标开侧栏可能扫到同窗口另一个标签。

### S-11 四个入口门槛各不相同

- 侧栏 `minSize=1/minShow=48`（`js/image-page.js:303-316`）；面板 `imgMinSize/minShow=48`（`js/image-panel.js:406-408`）；popup `imgMinSize/minShow=48`（`js/popup-videorod.js:2226-2229`）；悬停 `100/500/200`（`js/image-hover.js` + `js/lib-image-util.js:580-600`）。
- **影响**：同一页「侧栏 19 张、弹窗 7 张、面板 30 张」，用户判“嗅探不准”。

### S-12 图集滚动覆盖不足

- **证据**：只滚 `window`，不滚内部容器/虚拟列表/“加载更多”；`geo.moved=false` 立即 done（`js/background.js:1602-1620, 1888-1891`）；固定等 450ms（`:1501, 1854-1856`）；单页失败直接 error，方案里的“连续 2 页失败停”未实现（`:1846-1850`）。
- **影响**：长图集/懒加载图集抓不全或过早结束。

### S-13 图集状态全量读写

- **证据**：每滚一屏把整个任务（最多 1000 URL）全量读写 `chrome.storage.session`（`js/background.js:1537-1550, 1893`）。
- **影响**：大图集慢，且 SW 回收后可能重复跑（内存锁 `VR_ALBUM_RUNNING` 丢失）。

## 四、P1：落盘、去重、设置

### O-01 批量必须落资源库目录，但会静默回退

- **证据**：`decideMode` 在 FSA 未授权时回退 `chrome.downloads`（`js/library/save.js:140-147`）；下载器的文件名/目录在 ADR-040 后不可控。
- **影响**：文件落到浏览器下载目录，用户以为失败。
- **决策**：本项目采用「批量必须落资源库目录；未授权则阻止并引导授权」，见 ADR-080。

### O-02 `defaultDir` 设置不生效

- **证据**：popup 用 `settings.defaultDir` 拼文件名（`js/popup-videorod.js:2397`），后台只用 `vrImgSubdir` + `buildRelPath`（`js/background.js:1162-1181`）。
- **影响**：用户设置的自定义目录被忽略。

### O-03 去重键误判

- **证据**：`vrCanonMediaUrl` 对多数站点丢掉整个 query，只保留 `host+path`（`js/background.js:4741-4772`）。
- **影响**：不同图共用 path、靠 query 区分时会误判重复。

### O-04 图片线没有幽灵记录校验

- **证据**：见 D-02；`vrBulkSaveItem` 有等价实现（`js/background.js:4697-4709`），图片线没接。

### O-05 `imgSniff` 死开关 + popup「图片 N」恒 0

- **证据**：`imgSniff` 只写不读（`js/popup-videorod.js:26,276,326`）；图片计数按 `G.Type` 白名单，图片未启用（`js/init.js:63-73`）。
- **影响**：用户以为没图/没嗅探。

### O-06 命名四套并存

- 悬停/侧栏 `标题_序号`；面板 `标题`（无序号）；popup `带扩展名的标题`；微博 `vrBulkName`。
- **影响**：同一批图在不同入口落成不同命名，去重与用户识别都受影响。

### O-07 B-46 图片版未做

- 首页/信息流批量全用页面标题，无法按笔记/微博分组（`docs/BACKLOG.md:209`）。

## 五、P0：测试门禁缺口

### T-01 批量落盘套件不在门禁

- `e2e-all.py` 的离线套件只有 `e2e-grab`（弹窗扫描 10 条），没有 `cdp-image-test.py`、`cdp-image-batch-test.py`（35 条）、`cdp-image-panel-test.py`（46 条）、`cdp-image-album-test.py`（40 条）。见 `tools/e2e-all.py:40-51`。
- `health-check.py` 只跑 `test-image-batch.js` 纯逻辑 27 条（`tools/health-check.py:31-33`），不跑 `vrImgBatch`/`vrImgDownload`。

### T-02 现有套件接不进门禁

- `e2e-all.py` 的 `run_suite` 只传 `--port`，不设置 `VR_CDP`；四个图片套件的 `Cdp()` 默认读 `VR_CDP`（默认 9222）（`tools/cdp_client.py:13`）。
- `cdp-image-batch-test.py` 默认落盘目录是 `D:\personal\Downloads\video-rod\...`，开头 `clean_disk`（`tools/cdp-image-batch-test.py:336-342`）。**绝不能在 9480 真实 profile 上跑**。

### T-03 live 套件不覆盖图片批量

- `e2e-xhs-image` 实际测的是视频页，且在 `LIVE_SUITES`，普通 `--full` 不跑（`tools/e2e-all.py:53-55`）。
- `live-sites.json` 的 `local-image` 只验侧栏 2 张，不验批量落盘（`tools/live-sites.json`）。

## 六、ImageAssistant 1.70.7 源码对标

路径：`C:\Users\Administrator\AppData\Local\Twinkstar\User Data\Default\Extensions\odphnbhiddhdpoccbialllejaajemdio\1.70.7_0\`

| 能力 | 它怎么做（源码） | 我们的差距 |
|---|---|---|
| 全 frame | `manifest.json:22-27` `all_frames:true`，`document_start` | 图片组 `all_frames:false` |
| 三路网络嗅探 | `scripts/inspector.js`：劫持 XHR/fetch/`Image.src`，响应文本用图片扩展名正则提取，`image/*` 响应直接收 `responseURL`，每 512ms 批量回传 | `net-sniff.js` 只抓视频 + 小红书 |
| 响应头缓存 | `scripts/background.js` `_o_initHeadListener`：`webRequest.onHeadersReceived`，`type==='image'` 或 `content-type:image/*` 且 `content-length>0`，按 tab 收 imageMap，附 pageURL/pageTitle/referer/serial | `G.Type` 不含 `image/*`，网络图片为 0 |
| 多来源合并 | `_o_pushExtractedImage`：按 URL 合并 DOM/网络/Image 钩子，保留优先级与最早 serial；按域名记 referer | 只按 DOM 去重，无来源优先级 |
| 原图规则表 | `defaultRegexpUrlRule.properties`：60+ 条 `匹配${#^_^#}替换`，递归深度 4；微博 `/large/`、Pinterest `/originals/`、豆瓣 `/l/` 等 | 只有硬编码 `upgradeSinaimg` + 通用 query 剥离 |
| 全属性提取 | `scripts/script.js` `_o_digElement`：遍历元素所有属性（含 style 内 `url()`），正则提取后用 `new Image()` 预载验证可达才收 | 只扫固定 `DATA_ATTRS` |
| iframe | `_o_zhuruJSYongHash`：`webNavigation.getAllFrames()` 后逐 frame 注入并提取 | `executeScript` 不传 `allFrames` |
| 尺寸探测 | `scripts/imageExtractor.js`：并发 8 预载、失败重试队列、动态载入阈值、按尺寸排序；尺寸漏斗只隐藏不删除 | 扫描时一次性 `fillSizes` 60 张/2.5s |
| 下载 | `scripts/function.js` `_w_rebate`：逐张 `chrome.downloads.download({filename, conflictAction:'uniquify'})`；防盗链特殊场景用页面上下文 `imgSrcToBlob` 兜底 | fetch + FSA 写 + 哈希 + 入库全塞进单张链路，批量必超时 |

**结论**：它的强项是「网络层缓存 + 全 frame/全属性 + 候选校验 + 轻量下载」；我们扫描只做 DOM 一部分，下载层过度工程化。
