# beUI 能不能用？技术评估

> 日期：2026-11-04 ｜ 问题：「我们前端是否可以参考用 beui 组件库？会更好看一些」
> 结论：**不能直接引入，但它的 6 个动效手法值得抄，而且用纯 CSS 就能做。**

---

## 一、beUI 是什么（GitHub API 实测）

| 项 | 值 |
|---|---|
| 仓库 | `starc007/ui-components`（beui.dev） |
| 星标 | **1,920** ★，94 fork |
| 许可证 | **MIT**（可商用、可修改、可再分发） |
| 创建 / 最后提交 | 2024-01-31 / **2026-11-02**（活跃） |
| 定位 | "Motion components for React. Copy, paste, done." |
| 组件数 | 145 个 React 组件 + 71 个 React Native |
| **技术栈** | **React + Next.js + Tailwind CSS v4 + Motion（Framer Motion）** |
| 安装方式 | `npx shadcn@latest add @beui/xxx`，源码进项目 |

**质量判断：是个正经项目**，不是玩具。动效水准明显高于普通组件库，而且它考虑了键盘操作、触摸、"减少动态效果"偏好——这几点说明作者懂可用性，不只是炫技。

## 二、为什么不能直接引入

### 2.1 技术栈根本不兼容

| | 我们 | beUI 要求 |
|---|---|---|
| 框架 | **无**（原生 JS，17 个模块） | React 19 |
| 构建 | **零构建**，加载目录即用 | 必须 Vite / Next 构建 |
| 样式 | 手写 CSS 2981 行 | Tailwind CSS **v4** |
| 动效 | 手写 CSS transition | Motion（Framer Motion） |

### 2.2 引入的代价

不是"加个依赖"，是**三件事同时发生**：

1. **整个 UI 重写**。`library.html` 的 117 个 id、`ui.js` 的 51 个动态 class，全要改成 React 组件。
2. **项目从"零构建"变成"必须构建"**。扩展页面加载的是构建产物，改一行要重新打包——你现在"改完刷新就能看"的节奏会消失。
3. **MV3 的 CSP 限制**。`shadcn` 安装方式是把源码塞进项目，需要打包才能跑；不能像现在这样直接 `<script src>`。

**估值：这等于重做整个媒体库界面，工作量远超本轮"换皮"。** 而且会把一个已经能用、能随时回退的项目，变成必须维护构建链的项目。

### 2.3 一句话

> **为了"好看一点"，把项目从零构建改成 React + Tailwind，是拿架构换皮肤，不值。**

## 三、但它值得抄——6 个手法，纯 CSS 就能做

"好看"不是来自组件库，是来自**动效的时机和克制**。beUI 这几招我们可以直接学，一行 React 都不用引：

| # | beUI 的手法 | 用在哪 | 我们怎么做（纯 CSS/JS） | 收益 |
|---|---|---|---|---|
| 1 | **Morphing lightbox**（从缩略图位置放大成全屏） | 点封面进预览 | **View Transitions API** 或 FLIP：记录缩略图位置 → 预览层从该位置 scale 展开 | **最大**。现在预览是"啪一下全屏出现"，很廉价 |
| 2 | **Animated toast stack**（提示堆叠） | 下载完成、重命名成功 | 多个 toast 垂直堆叠，旧的往下推，而不是互相覆盖 | 中。批量操作时会连着出好几条 |
| 3 | **Expandable action bar**（操作条展开） | 批量选择条 | 现在 `batchbar` 是突然出现；改成从顶栏高度 0→auto 展开 + 轻微位移 | 中 |
| 4 | **Number animation**（数字滚动） | KPI 统计卡 | 数字变化时 `requestAnimationFrame` 补间，0.3 秒 | 小但显专业 |
| 5 | **Command palette**（⌘K 面板） | 原型已有 ⌘K 提示但没做面板 | 一个居中搜索弹层，可搜"跳到某平台 / 某作者 / 执行某操作" | 中。库大了以后比点侧栏快 |
| 6 | **Morphing modal**（弹窗从触发按钮形变） | 重命名 / 确认框 | `transform-origin` 设为触发按钮位置 + scale 从 0.9→1（我现在的弹窗已接近，只差 origin） | 小 |

**我建议先做 1 和 3**：这两个是你每次用都会看到、且最能拉开"专业感"差距的。2/4/5/6 可以后补。

---

## 四、如果真要上 React，得单独立项

不是不能做，是**要当成一个新项目来评估**：

| 要评估的 | 说明 |
|---|---|
| 构建链 | Vite + React 19 + Tailwind v4，产物进扩展 |
| 迁移范围 | 媒体库（library）+ 设置页（options）两个页面 |
| 迁移方式 | 逐个组件替换（可以渐进，新组件用 React 挂到旧页面上） |
| 风险 | 构建链坏了，整个扩展页面打不开；而现在是纯文件，坏一个模块不影响其他 |
| 收益 | 动效和组件成熟度、后续加功能更快 |

**我的判断：现在不该做。** 等虚拟滚动那次重构（本来就要动渲染层）时再评估，那时候一起换成本最低。

---

## 五、结论

1. **不能引入 beUI**——它是 React + Tailwind v4 的库，我们是零构建原生 JS，引入等于重写。
2. **可以抄它的动效思路**，6 个手法用纯 CSS 都能实现，其中「从缩略图放大进预览」最值得做。
3. **"更好看"的答案不在组件库，在动效时机**：什么时候动、动多久、动多少。这条我可以直接改进原型。
4. 如果哪天真要上 React，**单独立项评估**，不混在界面改造里。
