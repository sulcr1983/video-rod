# 去重引用方案 · 本地只存一份，下载只记引用（B-12 施工设计）

> 版本：v1.0 ｜ 日期：2026-11-04 ｜ 状态：**方案待苏哥确认后施工**
> 起因：苏哥提出「不同链接下载相同内容，本地只存一份，后面的只引用——和网盘原理一样」。
> 结论先行：**可行，这正是网盘秒传的原理（内容寻址 + 引用计数）**。推荐「库层引用」实现，反对「改文件名为 hash」的实现。
> 本文只做方案，不动页面（页面 redesign 归另一会话）。

---

## 一、一句话原理

```
下载完成 → 算内容指纹（SHA-256）
  ├─ 库里没有这个指纹 → 正常落盘，指纹记在库条目上
  └─ 库里已有这个指纹 → 【不写磁盘】只在库里加一条「引用」，
                         界面上照样出现一条素材（自己的标题/来源/时间），
                         物理文件还是原来那一份
```

和网盘「秒传」一模一样：第二个人上传同样的文件，服务器只记一个指针。

## 二、两种实现，选哪个

| 方案 | 做法 | 优点 | 致命缺点 | 判定 |
|---|---|---|---|---|
| **A. 库层引用** | 物理文件保持原路径原名字（平台/博主目录），库里多条素材记录指向同一份文件（同 `hash`） | F 盘目录依旧人类可读；下载流程几乎不动；和现有 IndexedDB 模型天然兼容（加两个字段） | 删除/重命名要定义「引用计数」规则（本文第四节） | ✅ **采用** |
| B. 内容寻址（CAS） | 文件全部改存 `content/<hash>.ext`，文件名变 hash | 物理上最纯粹 | **文件名失去可读性**，毁掉「下载到文件夹、按平台/作者分目录、自定义命名」的产品根基；资源管理器里全是乱码名 | ❌ 不做 |

## 三、命中流程（下载时）

1. 下载完成（`downloads.onChanged state=complete`，现有钩子）。
2. **异步分块**计算 SHA-256（WebCrypto `crypto.subtle.digest`，128KB 一块读，不整读进内存，不卡 SW）。
3. 查库 `hash` 索引：
   - **未命中** → 正常入库（现有逻辑），条目写入 `hash` 字段。
   - **命中** → 删除刚落盘的重复文件，**只写一条库条目**：`relPath` 指向已有文件的路径，`hash` 同值，`isRef: true`，自己的 title/pageUrl/dlAt 照记。UI 提示「内容已存在，已建立引用（0 秒、0 空间）」。
4. 命中判断在 hash 算完之后，所以**秒传发生在落盘之后**（先下后删）。不做「下载前预判」（URL/大小预判只能降低概率，做不可靠的拦截反而误事）。

## 四、必须定死的四条规则（引用语义）

| # | 规则 | 定义 |
|---|---|---|
| R1 | **删除 = 删引用** | 删素材只把这条引用进回收站；物理文件在**最后一条引用被清空**时才真正删除（引用计数=同 hash 条目数）。恢复=恢复引用，文件一直都在 |
| R2 | **重命名 = 只改这条引用的显示名** | 库条目加 `displayName`，物理文件名不动（否则会连带改掉所有引用的文件）。信息栏「路径」显示物理路径，素材名显示 displayName |
| R3 | **移动/整理 = 不搬物理文件** | 收藏夹/标签/分类都是库层视图，与物理位置无关（现有「收藏夹是视图不是位置」原则不变） |
| R4 | **文件被用户在资源管理器手动改名/删除** | 沿用现有「文件缺失」态：引用变灰、提示路径失效，不自动清理 |

## 五、统计口径（避免「删了怎么还占空间」的困惑）

- **素材数**：引用照常计数（界面逻辑不变）。
- **大小**：卡片/信息栏显示「单份大小」；**库统计区分两行**：`逻辑 486 MB（36 条）`、`物理占用 210 MB（去重后实际占盘）`。侧栏底部那一行小字放得下。

## 六、老文件怎么办（不强制一次算完）

- 已入库的历史文件没有 hash：**懒补算**——后台低优先级队列逐个补（设置页一个「补算指纹」入口 + 进度条），算完自动合并发现的老重复（合并动作先列清单让用户确认，不偷偷删）。
- 新下载从上线起全部带 hash。

## 七、与现有两层防重的关系（三层合拢）

| 层 | 拦什么 | 现状 |
|---|---|---|
| L1 URL 级（vrMediaSeen 账本） | 同一个链接下两次 | ✅ 已有，保留 |
| L2 hash 级（本方案） | 不同链接、内容相同 | 🆕 本方案 |
| L3 库内事后查重 | ~~补救清理~~ | ❌ 按钮已删，被 L2 取代 |

## 八、边界与风险

1. **大文件 hash 耗时**：1GB 视频 SSD 约 1-3s（异步，不阻塞界面）；正在算的文件短暂处于「未保护」窗口，可接受。
2. **MD5 vs SHA-256**：用 **SHA-256**（非安全场景 MD5 也够，但现代硬件差距可忽略，一步到位）。
3. **极小概率碰撞**：SHA-256 工程上可忽略；再加一道「大小相同才比 hash」的双保险，大小不同直接判不同。
4. **FSA 直写路径**（YouTube 管线等）同样走 `ingest` 钩子，hash 逻辑一致。

**验收用例（DD 系列）**：
- DD-1 同内容不同链接二次下载 → 秒完成、物理文件数不变、库多一条引用、提示正确
- DD-2 删除其中一条引用 → 物理文件仍在；删到最后一条 → 进回收站；清空回收站 → 文件删除
- DD-3 恢复引用 → 素材回来且能播放
- DD-4 重命名一条引用 → 只改显示名，其他引用与物理文件不变
- DD-5 统计双口径正确（逻辑 ≠ 物理，差值=被引用份数）
- DD-6 埋点异常不影响下载（沿 META-6 红线：hash 失败=照常落盘入库，只是没有防重保护）
- DD-7 手动改物理文件名 → 引用变「文件缺失」，不误删
