**值得做，而且这次做对了。**
主路径已经能作为个人日常工具使用；这次黑盒验收还抓到一个**真实的删除/恢复数据风险 bug**，已修复并验证。

- 干净 profile 首次使用：**48/48 PASS**。
- 真实 35 条资源库回归：排序 **14/14**、移动 **9/9**、重命名 **9/9**、只读权限 **8/8**。

**发现并修复的真实 bug：**

> `VRTrash.remove/restore/purge` 把带 `video-rod/` 前缀的索引路径直接传给指向「库根」的 FSA 句柄。
> 后果：删除时可能**只删了 DB 条目，文件没有进回收站**；恢复时找不到回收站批次。
> 修法：物理文件操作前先剥掉索引首段 `video-rod`，manifest/DB 继续保留原始 relPath。
> 回归：OPFS 模拟库根句柄，删除/恢复 7 项全部通过。提交 `7e2ce2b`。

## 3. 这次抓到的真实问题

### P0/P1：回收站路径前缀 bug（已修）

**代码：** `js/library/trash.js`。
**现象（修复前）：** 用库根句柄删除 `video-rod/...` 条目时，`exists(handle, relPath)` 找到的是 `库根/video-rod/...`，真实文件在 `库根/...`，于是被判定“文件不存在”，走 `cleaned++`，**只删 DB 条目，文件留在原地**；`restore` 找不到批次。
**影响：** 用户以为删除成功，实际文件没进回收站；DB 条目消失后无法恢复。
**修复：** 新增 `stripPrefix(rel, prefix)`；`remove/restore/purge` 的物理操作使用剥掉 `video-rod/` 后的路径；manifest/DB 继续保留原始 relPath。
**验证：** OPFS 库根句柄：`remove moved=1`、DB 条目消失、文件进回收站、没有多一层 `video-rod`、`restore restored=1`、文件回原位、DB 恢复，7/7 PASS。

### 不是产品 bug 的测试侧问题

- 图片悬停按钮有 700ms 延迟，测试最初等 0.8s，偶发误判；已改为真实 CDP 鼠标移动 + 重试。
- 同一页面同时有图片和视频时，图片悬停会被“视频页抑制”逻辑关掉；测试改为图片页/视频页分开。
- 首次下载的两条记录同一分钟，old/new 排序无法区分；真实 35 条排序已覆盖。

## 5. 独立判断

### 这个项目值不值得做“彻底清查”？

**值得做一次，但不该做成两周的全平台全功能 QA。**
这次 48 项首次使用黑盒已经证明：主路径（下载→入库→预览→信息→搜索/排序）是通的；并且能抓到工程测试漏掉的真实删除 bug。

### 现在的产品状态

- **可以作为个人日常工具使用**：下载、自动入库、浏览、预览、信息、搜索/排序、缺失提示都能走通。
- **删除/移动是“授权后才可用”**：没有目录句柄时按钮禁用并说明原因，这是正确设计；但首次用户必须先授权，否则会觉得“怎么不能删”。
- **还不是生产级产品**：真实 picker、批量删除、YouTube、真实站点、超大文件/海量库仍未闭环。
- **最大的剩余风险不是 UI，而是“权限/真实路径”这一类端到端问题**：这次回收站前缀 bug 就是典型。

### 建议下一步（按优先级）

1. **真实 picker + 授权后删除/移动/恢复**：手工点一次系统目录选择器，验证授权后按钮启用、真实文件进出回收站、批量删除/恢复。
2. **真实站点抽样**：X、微博各一条下载；YouTube 一条 1080p+，确认无弹窗、进度、声音。
3. **首屏缩略图与大数据性能**：P1 的缩略图/分页/虚拟滚动，不要和 P0 混在一起。
4. **首次使用引导**：在 popup/页面浮层也提示“先授权素材目录”，不要等用户打开库才发现只读。
5. **测试工具**：把 `first-run-audit.py` 作为发布前冒烟；不要每次全量跑，避免本地 profile/下载目录积累。
