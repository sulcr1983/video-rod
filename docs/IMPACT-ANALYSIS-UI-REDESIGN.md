## 五、技术方案存在的问题

以下四条是**方案文档与当前代码不一致**的地方，其中前三条是我自己写的文档里的错，必须指出。

### 5.1 【严重】溯源方案的存储位置已经过时

`docs/MEDIA-METADATA-PLAN.md` 写的是：

> SW 写 `chrome.storage.local` 队列 → `library.html` 合并进 **`_index/meta.json`**

**但合并后媒体库已改用 IndexedDB**（`db.js` 的 `file` / `thumb` store），不再有 `_index/meta.json` 这个真源。

**原因**：该文档写于合并前（当时是单文件库 + `_index/index.json`），合并后未同步。

**最小改动**：不新建 `meta.json`，**直接在 IndexedDB 的 `file` 条目上加字段**。落地更简单（少一次文件读写、少一个对账环节），且 `mergeEntry()` 已有保留机制。

### 5.2 【严重】推荐 Media Chrome 是过度设计

`docs/MEDIA-VIEWER-PLAN.md` 建议引入 Media Chrome（242 KB）承载视频控件。

**问题**：现有 `libVideoCtl` 已经有 8 个控件（播放/时间/进度/静音/音量/倍速/连播/全屏），且 `video.js`（186 行）已经把这些事件接好了。引入 Media Chrome 是**替换一套能用的东西**，要重接全部事件，收益只有"控件长得更标准"。

**我们的 CSS 本来就是按自己的设计系统写的**，引入外部控件层反而要和它抢样式（方案里也写了"覆盖 media-chrome 的 CSS 变量"——这就是信号：需要覆盖它，说明不该用它）。

**最小改动**：保留 `libVideoCtl`，按原型补 4 个键（逐帧、画中画、倍速快/慢、静音键）。**不引库。**

**唯一例外**：若将来要做"直播流 / DRM / 多音轨"，再考虑换控件层。现在不需要。

### 5.3 【严重】"整体重写 CSS"违反最小改动

原型落地建议是"`css/library.css` 整体重写（197 行 → 约 700 行）"。但这个估计是**基于归档的单文件版**（当时 197 行），**当前 CSS 是 2981 行**，且 `ui.js` 有 30+ 处动态生成 class。

整体重写会踩三个坑：
1. 动态生成的 class 名（`sideItem()` / `platIcon()` / `creatorIcon()` / `dayBucket()` 等）容易漏
2. 回收站/批量/重命名/迁移四块的样式分散在 `library.css`，重写易丢
3. 一旦视觉不对，无法只回退一部分

**最小改动**：**分两步走**——
- 第一步只换 `:root` 设计令牌（颜色、圆角、阴影、字号、间距），结构一行不动
- 第二步逐组件改（卡片 → 列表 → 信息栏 → 控件条）

令牌替换能拿到 70% 的视觉提升，风险接近零，且可单独回退。

### 5.4 【中】动图方案应该先验原生

方案文档倾向 `gifuct-js`（+40 KB 依赖），但 Chrome 有原生 `ImageDecoder` API，可解 GIF / WebP / APNG 三格式。

**若原生可行，则不需要引入任何依赖**，只写一个薄封装。方案里已标"待预研"，但**正文措辞偏向引库**，容易让执行者直接装依赖。

**处置**：预研结论出来前，不装任何依赖。

## 九、最终判断

### 可以开始实施吗？

**现在不行。** 有三个前置条件：

1. **批次 0（实机验证）必须先过**。合并结果从未加载过，这是硬门槛。
2. **三份文档需先修订 3 处**（都是方案与代码不一致，非改需求）：
   - `MEDIA-METADATA-PLAN.md`：`_index/meta.json` → IndexedDB `file` 条目字段
   - `MEDIA-VIEWER-PLAN.md`：删掉"引 Media Chrome"，改为在 `libVideoCtl` 上补键
   - `PROTOTYPE-MAPPING.md`：§7 第 1 步"CSS 整体重写"改为"令牌替换 + 逐组件"
3. **一份 10 条人工回归清单**（无测试情况下的最低保护）。

### 需要调整需求文档吗？

**需求本身不用改。** 这次要的东西（信息齐全、能回溯、查看器好用、动图能做）都是合理的，原型也验证过。

**要改的是技术方案的实现路径**，而且是往"更小改动"的方向改，不是加需求。

### 一句话结论

> 需求可以做，原型也能直接用。但**先验合并、再改文档三处、然后按 8 个批次小步走**。不要一次性重写 CSS，不要为了控件好看去引一个替换现有功能的库——那才是真正的重复造轮子。
