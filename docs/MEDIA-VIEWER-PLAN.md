# 媒体查看器方案（播放器 / 图片 / GIF）

- **日期**：2026-11-04 ｜ **状态**：📋 方案评审中（等苏哥拍板后施工）
- **范围**：媒体库预览层的三类媒体查看体验
- **铁律**：先搜成熟控件，评估后能复用就复用；不复用时必须写明理由

---

## 0. 一句话

**视频缺的不是播放引擎，是控件层；图片我们已经有八成了；GIF 是唯一真正缺的一块。**

---

## 1. 现状诊断（先看清楚缺什么）

现有 `js/library.js` 预览能力实测：

| 能力 | 现状 |
|---|---|
| 图片缩放 | ✅ 滚轮（0.4–4×）、双击切 1×/2×、`+` `-` `0` 快捷键 |
| 图片拖动 | ✅ 鼠标拖拽平移 |
| 图片旋转 / 适应窗口 / 1:1 | ❌ 无 |
| 缩放百分比显示 | ❌ 无（用户不知道当前是几倍） |
| 视频 | ⚠️ 直接用浏览器原生 `<video controls>` |
| 视频倍速 | ⚠️ 只有右键菜单里的原生选项 |
| 逐帧 / 快捷键提示 | ❌ 无 |
| GIF | ⚠️ 当图片用 `<img>`，**无法暂停、无法逐帧** |
| 键盘 | ✅ ↑↓ 切换、←→ 快进、Space、F、I、Esc |

**结论**：图片八成熟、视频零成熟（靠浏览器）、GIF 完全没做。

## 2. 调研：四个候选，两个已经被时代淘汰

| 库 | 定位 | 许可 | 体积(gzip) | 打包形态 | 最后发布 | 结论 |
|---|---|---|---|---|---|---|
| **Plyr** | 视频 UI | MIT | 32.6 KB | UMD | — | ❌ **已官方废弃**，只接安全更新；作者去做 Video.js 10 了 |
| **Vidstack / Media Chrome** | 视频 UI（Web Components） | MIT | 74 / 41 KB | IIFE 可用 | 2026-10（活跃） | 🟡 已并入 Video.js 10，但仍维护 |
| **Video.js 10** | 全量播放器 | Apache-2.0 | 25 KB（HTML 无 ABR） | ESM / `@videojs/html` | **2026-10-01 GA** | 🟡 最新最强，但刚 GA，插件生态未成熟 |
| **PhotoSwipe 5** | 图片灯箱 | MIT | 17 KB | ESM | **2024-05** | ❌ 30 个月未发版，且只做图片（视频要插件） |
| **lightGallery 3** | 图片+视频画廊 | **GPLv3** / 商业 | 19 KB | UMD | 2026-10 | 🟡 功能最全，但要整包接管 UI |
| **gifuct-js** | GIF 帧解析 | MIT | 小 | UMD | 稳定 | ✅ **唯一解**，GIF 想暂停就必须解析帧 |

### 三个关键事实

1. **Plyr 不能选了**。官网首屏原话：*"Plyr is now deprecated and receives security updates only. Use Video.js 10 for new projects."* 如果按老教程选它，等于一上来就接手一个弃维护的库。

2. **lightGallery 是 GPLv3** —— 对多数项目是红线，但我们本来就是 GPL-3.0，**法律上完全兼容**。它功能最全（缩略图、缩放、旋转、视频、键盘、触摸），代价是整包接管预览层 UI。

3. **PhotoSwipe 的核心只有图片**。视频、缩略图条、说明文字都是插件或自己写；而且它要求**预先知道每张图原始宽高**才能做开场动画。我们的素材是本地文件，尺寸要异步读，正好踩在它的前提上。

## 3. 选型决定

### 3.1 视频 → **Media Chrome**（只取控件层）

**为什么不用 Video.js 10**：它是完整播放器，接管 `<video>` 元素和状态。我们已经有 `play/pause/currentTime/全屏` 的逻辑、有自动播放带声的兜底，接进来要重写一遍。而我们的本地文件**根本不需要 HLS/DASH/DRM/ABR**——Video.js 90% 的复杂度对我们无用。

**为什么是 Media Chrome**：它的定位原话是"不是播放器，是控制面"——只提供按钮、进度条、音量、时间、设置菜单，套在**你自己已有的 `<video>`** 上。这正是我们要的"只换壳、不动引擎"。

- 引用 `dist/iife/all.js`（242 KB 未压缩 / ~41 KB gzip），`<script>` 直接引，无需构建
- MIT，本地打包，无 CSP 问题
- 风险：已并入 Video.js 10。**缓解**：都是 Web Components，真到那天迁移成本低；且我们会用一层 `data-*` 隔离，不直接写死它的内部 DOM

**不选的方案**：自己写控件条（约 200 行）——这属于造轮子，除非 Media Chrome 实测不可用。

### 3.2 图片 → **不引入库，补三个功能**

现有实现已经覆盖缩放/拖动/双击/快捷键，缺旋转、适应、1:1。

- PhotoSwipe 会砸掉信息栏、胶片条、标签、重命名/移动——这些是我们的产品壳，不是它的
- 缺的三项是纯 CSS transform + 一个按钮，**加约 30 行**，不构成"造轮子"
- 如果非要引，只有 `Zooming`（MIT, ~3 KB）值得考虑，但它只做缩放平移——我们已经有更好的键盘/滚轮接入了

**判断**：图片这块属于"轮子已经在自己手里"，不需要再买一个。

### 3.3 GIF → **gifuct-js**（唯一必须新增的依赖）

GIF 想暂停/逐帧，只有一条路：把 GIF 拆成帧，用 canvas 自己渲染。

- `gifuct-js` 2.1.2，MIT，UMD，解析出每一帧的像素与延时
- 自己维护一个 `requestAnimationFrame` 播放循环 + 当前帧索引
- 好处：暂停、逐帧、循环次数、播放速度都能控
- 成本：一张 1600×1200 的 GIF 解到内存约 7.7 MB/帧，**必须设上限**（>200 帧或 >20 MB 时退回原生 `<img>` 播放）

## 5. 视频控件条设计

三条原则：**能悬停就收起、能一个按钮就别开菜单、所有按钮有 title 和 aria-label**。

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│                    （画面，点按播放/暂停）                     │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│  │ 进度条（悬停显示时间气泡）
│  └────────────────────────────────────────────────────────┘  │
│  ▶   01:23 / 03:45      ⏮5 ⏭5   🔊▁▂▃   1×   ⛶   ▣   ⋯     │
└──────────────────────────────────────────────────────────────┘
```

- 进度条：悬停显示 `mm:ss` 气泡；缓冲进度用浅色第二层
- 无操作 2.5 秒后控件淡出，鼠标移动立刻回来
- 倍速按钮直接循环，不开菜单（菜单要多一次点击）
- 移动端（<760px）只保留 ▶ / 时间 / 全屏

## 6. GIF 播放器设计

```
┌────────────────────────────────────┐
│                                    │
│          （GIF 画面 canvas）        │
│                                    │
│  ⏸  ▶  第 12 / 86 帧   ⟳ 无限  1× │
└────────────────────────────────────┘
```

- 默认自动播放（与 `<img>` 行为一致），**不改变现有直觉**
- 一旦用户按了暂停，暂停状态保持到切换媒体
- 帧计数显示 `第 N / M 帧`，让"逐帧"有意义
- 超过 200 帧或 20 MB 时不接管，直接显示 `<img>` 并标注「过大，使用系统播放」

## 11. 信息栏信息层级（v3：分组 + 对齐，信息一个不删）

### 走过的弯路（记录在案）

第一版把「文字堆在一起」理解成了「信息太多」，做成了**删字段 + 折叠**，结果把保存时间、分辨率分项、作品 ID、路径全藏起来了。苏哥原话："**我要信息！但是不要乱七八糟放着！**"

所以正确解法不是删，是**给同样的信息建立结构**：

- 同样的字段，不删一个
- 用**分组标题**切开（文件 / 来源 / 标签）
- 每组内用 **`<dt>` 标签 + `<dd>` 值 两列对齐**，形成可扫读的表格感
- 标签列固定 58px 宽、灰色小字；值列深色、稍大——一眼能找到"我要看哪个值"
- 只有分组标题可以小，因为它只是分隔，不是内容

### 与「堆在一起」的区别

| 之前（乱） | 现在（有结构） |
|---|---|
| 四个方块平铺，每块都是「标题 + 值」，视觉重量相同 | 六行 `标签 / 值`，标签退成灰色小字，值统一左对齐 |
| 来源块是一整个大卡片，与其它区块抢注意力 | 来源降为「组」，和其它组同权重，靠分组标题区分 |
| 按钮三行大块 | 一行四键 |
| 字段类型混杂（时间、尺寸、ID 混排） | 按语义分组，同类字段挨着 |

### 状态徽标四态（不假装「已记录」）

| 状态 | 条件 | 显示 |
|---|---|---|
| 完整 | 原帖 + 直链都有 | 绿「已记录」 |
| 部分 | 只有其一 | 灰「部分记录」 |
| 未记录 | 都没有 | 灰「未记录」 |
| 推断 | 目录反推 | 灰「推断」 |

> 之前只要 `source === 'download'` 就显示「已记录」，但微博这类拼不出原帖的记录实际是空的——徽标必须反映**真实完整度**。
