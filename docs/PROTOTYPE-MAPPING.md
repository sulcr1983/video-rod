> 版本：v1.0 ｜ 日期：2026-11-04 ｜ 状态：待苏哥确认原型后进入施工
> 原型：`deliverables/prototypes/media-library-redesign-v1.html`
> 代码基线：`merge/remote-20261104`（合并后，媒体库为模块化版本 `js/library/` 17 个模块）
> 本文解决一个具体问题：**原型是"纸上的目标状态"，代码是"已实现的一部分"，中间必须先有一张对照表，否则落地时会重复做、做错、漏做。**

## 0. 一句话结论

原型不是从零画的新东西——**代码已经实现了原型里约六成的结构**，但两者用的是两套命名（原型 `pv*`、代码 `lib*`），而且**代码里有一批原型没画的功能（回收站、右键星标、创作者导航），直接照原型改会把它们弄丢**。

所以落地不是"照原型重写"，而是三件事：**改视觉、补缺口、别弄丢已有的**。

### 2.1 「分辨率」是唯一一次能拿到真值的机会

查证结果：

- `js/library/db.js:145` 的 `putThumb(thumbKey, blob, w, h)` —— 存的是 **canvas 尺寸（缩放后）**，不是原图尺寸
- `js/library/indexer.js` —— **全文件没有一行写入 `width` / `height`**（只有 `mergeEntry` 负责"保住旧值"，但从来没人写过）
- `js/library/thumbs.js:124/128` —— 生成缩略图时**能看到 `naturalWidth` / `videoWidth`**，也就是真实分辨率，但只用来算 canvas 比例，没回写条目

**这意味着：分辨率不是"取不到"，是"看到了没存"。**

而索引一旦建完，之后不会再解码每个文件——**错过生成缩略图那一刻，以后只能重新解码全库才能补回来**。

所以这条要**趁现在顺手补**，改动量一行：

```js
// thumbs.js 生成成功后，把真实宽高回写到条目
entry.width = w; entry.height = h;   // w/h 取 naturalWidth / videoWidth，不是 canvas 的
```

## 6. 「标签」到底是丢了还是没丢

我上一轮跟苏哥说"标签功能丢了"，**这句话不准确，纠正如下**：

| 层 | 现状 |
|---|---|
| 数据库字段 | ✅ **有**：`indexer.js:228` 的 `tags: []`，`db.js` 建了索引 |
| 重建索引时保留 | ✅ **有**：`mergeEntry` 显式保住 `old.tags` |
| 读写接口 | ❓ 待确认（`db.js` 是否有按标签查） |
| **界面入口** | ❌ **没有**：信息栏没有标签区，卡片不显示标签 |

**结论：不是"丢了"，是"只有仓库没有货架"。** 补一个标签区（原型已有设计）+ 写入接口即可，成本远小于重做。

同理**查重（SHA-256）**：本地单文件版有，模块化版没有。查重需要读完整个文件算哈希，成本高，建议列为独立任务，不塞进这次界面改造。

## 12. 作者名字与作者 ID：缺失时怎么处理（2026-11-04 补充）

### 12.1 结论先说

**不是「留空还是隐藏」的二选一，而是先把「缺」分成三类，三类处理完全不同。** 判错的后果是：把「平台没有这个概念」标成红色的错误，会让用户以为工具坏了。

| 缺的类型 | 例子 | 这是缺陷吗 | 处理 |
|---|---|---|---|
| **平台本身没有** | 通用网页图片（右键存图）、图床 | **不是** | 名字显示「未知来源」（灰），账号相关全部隐藏 |
| **平台有、这次没抓到** | 接口没返回、页面改版、DOM 变了 | **是** | 名字显示「未获取」（红底）+ 重试按钮，让人看见并能补救 |
| **有，但和名字是同一个** | Instagram `username`、X `@handle` | 不是 | **只显示一次**，不重复 `NASA @NASA` |

### 12.2 一条通用原则

> **主体信息（昵称）缺失 → 显示状态；辅助信息（ID）缺失 → 直接隐藏。**

理由：
- 昵称是这一行的主体，空着会让整行塌掉，看起来像渲染坏了。**必须有个说法。**
- ID 是辅助信息，它的价值是"能拼出主页链接、能去重"。没有就是没有，**留个空壳反而像 bug**。
- 更关键：`@` 后面空着，是所有界面里最典型的"半成品感"来源。

### 12.3 字段模型：ID 要拆成两个，不能只有一个

查证抖音的接口返回（`js/douyin.js:104-107`），**同一个平台一次给了三种 ID**：

| 抖音字段 | 是什么 | 用户能用来搜吗 |
|---|---|---|
| `unique_id` / `short_id` | 抖音号 | **能** |
| `uid` | 数字 ID | 不能 |
| `sec_uid` | 加密串 | 不能（只能拼主页链接） |

所以"authorId"这一个字段是**装不下**的。改成三个：

| 字段 | 含义 | 显示位置 |
|---|---|---|
| `author` | 昵称 | 作者行主体（必显示，缺失给状态） |
| `authorHandle` | **可读账号**：@handle / 抖音号 / 小红书号 | 作者行，仅在存在且不等于名字时显示 |
| `authorUid` | **内部 ID**：uid / sec_uid / userId / mid / IG pk | **来源组「作者 ID」行**，缺失则整行隐藏 |
| `authorState` | `ok` / `missing` / `unsupported` | 只影响显示，不显示给用户 |

**为什么内部 ID 不放在作者行**：微博的 `uid` 是一串数字、小红书的 `userId` 是 24 位 hex，放在名字旁边只会挤占空间。但它对"拼主页链接、去重、以后再抓"有用，所以放进「来源」组——**信息不丢，但不抢位置**。这符合之前定的"信息一个不删，但要有结构"。

### 12.4 四种情形，界面上长什么样

| 情形 | 作者行 | 来源组「作者 ID」 | 主页链接 | 来源徽标 |
|---|---|---|---|---|
| 名字 + 可读账号都有，且不同（抖音、YouTube） | `奇趣蛋蛋 @qqdd` | 有 uid 就显示 | 可点 | 按完整度 |
| 名字 == 账号（Instagram、X） | `yuki.photo` + 灰色副标题 | 有就显示 | 可点 | 按完整度 |
| 名字有、账号没抓到 | `奇趣蛋蛋`（无 @） | **隐藏** | 拼不出，不可点 | **降为「部分记录」** |
| 名字都没抓到 | 🔴`未获取` + ⟳ | **隐藏** | 不可点 | **降为「部分记录」** |
| 平台没有这个概念 | 灰色`未知来源` + 灰色 `?` 头像 | **隐藏** | 隐藏 | 「未记录」 |

### 12.5 两个连带规则（不做会出错）

**① 来源徽标必须把「作者缺失」算进总评**
之前只要「有原帖 + 有直链」就显示绿色「已记录」，但作者压根没抓到——这是假信息。规则：`authorState === 'missing'` 时，徽标最高只能到「部分记录」。

**② 空作者不能算「同作者」**
否则一堆没有作者的网页图片会被归成"同一个作者"，同作者区块里出现一堆互不相关的素材。

### 12.6 和代码的接口

| 原型 | 代码落点 | 说明 |
|---|---|---|
| `renderAuthorRow(f, s)` | `js/library/lightbox.js` 的 `paintFacts()` | 现有 12 项平铺，作者是其中一项；改造时把作者从 facts 里提出来单独渲染 |
| 「作者 ID」行 | 同上，`facts` 新增一项 | 只在有 `authorUid` 时出现 |
| 重试按钮 | 新增 | 触发一次"补抓作者信息"；需 `try/catch`，失败只提示不阻断 |
| `authorState` | `indexer.js` 入库时写入 | 由抓取层决定；抓取层没给就按"有作者=ok，无作者=unsupported"兜底 |

### 12.7 一个额外发现：可以从路径反推

现有目录命名规则是 `平台/作者名(@账号)/类型/`。所以**即使字段丢了，路径里可能还留着账号**（`douyin/qqdd/` → handle `qqdd`）。

这可以作为第三顺位的补救来源：字段 → 页面 → **路径反推**。
但要注意：反推出来的只能算「推断」，徽标上要标出来，不能当成"当时抓到的"。

> 原型里刻意做了自洽：账号没抓到时，目录名只用名字（`douyin/奇趣蛋蛋/`），不会出现"路径里有账号但字段没有"这种自相矛盾。

## 13. 播放速度控件（2026-11-04 新需求）

### 13.1 档位

`0.1× / 0.25× / 0.5× / 0.75× / 1×（正常）/ 1.25× / 1.5× / 2×`，共 8 档。

为什么是这 8 档，而不是常见的 0.5 / 1 / 1.5 / 2：

- **0.1× 和 0.25×** 是"看清动作"用的——舞蹈分解、维修教程、手部动作；0.5× 看不清细节。
- **0.75×** 是"听清台词"用的——比 0.5 自然、比 1 慢，外语听力常用。
- **1.25× 和 1.5×** 是"快速过一遍"——1.25 几乎无感，1.5 是多数人的上限。
- 2× 封顶：再快人耳已经无法分辨内容，没有实用价值。

### 13.2 交互（原型已实现）

| 操作 | 行为 |
|---|---|
| 点控件条的 `1×` | 从控件条上沿弹出浮层，两列 8 档，当前档高亮 + 勾选，顶部显示当前值 |
| 点某一档 | 立即生效，浮层关闭 |
| `>` / `<` | 快一档 / 慢一档，到头提示「已经是最快 / 最慢」 |
| `Esc` | **先关浮层**，不退出预览（逐层退出） |
| 点空白 | 关闭浮层 |
| 切换素材 | 倍速**保持**（这是观看偏好，不是单条属性） |

浮层定位贴着**控件条上沿**，不是贴按钮——贴按钮会让浮层底边探进控件条内部、被盖住半截。

### 13.3 落地要点（给开发）

| 项 | 做法 | 坑 |
|---|---|---|
| 真实生效 | `videoEl.playbackRate = r` | Chrome 支持 0.0625–16，8 个档位全在范围内 |
| 音调 | `videoEl.preservesPitch = true`（默认值，别关） | 关掉后 0.5× 会变闷、2× 会变尖，像快进录音带 |
| 音频 < 0.5× 的体验 | **属于正常现象**：时间被拉长，声音必然发闷 | 不要试图"修复"，业界都这样（YouTube 也一样） |
| 动图倍速 | 帧间隔 `120 / r`，下限 40ms | 低于 40ms 浏览器画不过来，会掉帧 |
| 切素材 | `playbackRate` 要**重新设一次** | 换了 `src` 的 `<video>` 会把 `playbackRate` 重置为 1 |
| 记忆 | 存 `chrome.storage.local`，key `vr.playbackRate` | 别存进索引库，它不是素材属性 |

### 13.4 一个没做但值得考虑的

**按住某个键临时加速**（类似播客的「跳过广告」）：按下 `Shift+>` 临时 2×，松开回原速。对"快速扫过片头"很有用，但属于锦上添花，先不做。

## 14. 收藏夹（2026-11-04 新需求，一级栏目）

### 14.1 先把三件东西分清楚

用户说"收藏夹"时，可能指三种完全不同的东西。分不清就会做错：

| | 是什么 | 排他吗 | 谁决定 | 例子 |
|---|---|---|---|---|
| **目录树** | 文件**实际存放位置** | 排他（一个文件只在一个目录） | 下载规则自动生成 | `X/NASA/videos/` |
| **收藏夹** | 手动组织的**集合**，文件不动 | 不排他（一个素材可在多个夹） | 用户手动 | 「给客户的」「旅行素材」 |
| **标签** | 检索用的**属性** | 不排他 | 用户手动，多而碎 | `太空` `4K` |
| **星标** | 快速标记 | 布尔，只有"标了/没标" | 用户一键 | — |

**核心判断：收藏夹是「视图」不是「位置」。**

理由：我们已经有自动生成的物理目录（平台/作者/类型）。如果收藏夹再做成一排他的文件夹，用户会不知道素材该放哪，而且会和自动目录打架——同一个文件到底归"目录"还是归"收藏夹"？

所以：**素材文件永远不动，收藏夹只记 id**。删掉收藏夹不会删文件，重命名收藏夹不会动路径。这一条要写进 UI 文案里，否则用户不敢删。

### 14.2 星标怎么办：做成「规则型系统收藏夹」

原来星标是右键菜单里一个开关，加完之后**没有出口**——你不知道标了哪些，也不知道标了有什么用。

现在「已加星标」是收藏夹列表的第一项，**规则型**：成员不是手动加的，而是"所有 `starred === true` 的素材"。

好处：
- 星标动作有了归宿，加了就能看到
- 不用为星标单独设计一个入口/页面
- 与手动收藏夹并列，用户心智统一："要找东西就去收藏夹"

代价：不能重命名、不能删除、不能排序（固定第一位）。这些在 UI 上要明确——它没有操作按钮，并标注「自动」。

### 14.3 界面结构

**侧栏（一级栏目，放在资源树之上）**

```
收藏夹                            [+]
  ★ 已加星标                    12     ← 黄星、自动、不可编辑
  ▸ 旅行素材                     8     ← 书签图标
  ▸ 教程待看                    23
  ▸ 给客户的                     5
  全部收藏夹（7）                      ← 超过 5 个才出现

资源树                          37
  ...
```

为什么放资源树**之上**：收藏夹是"我挑过的"，资源树是"系统分的"。人打开库的第一反应是"我上次留的东西在哪"，不是"按平台翻"。**按使用频次排，不按数据结构排。**

为什么侧栏只显示 5 个：侧栏高度有限，且资源树是主浏览区。超过就进管理抽屉——**不给列表加滚动条**，滚动条会让侧栏看起来像没设计完。

**收藏夹视图（复用主网格，不新建页面）**

```
收藏夹 / 旅行素材                     ← 面包屑，「收藏夹」可点返回
旅行素材  5 项
[重命名] [复制清单] [删除收藏夹]
川西、折多山、路上随手拍 · 5 个素材 · 68 MB · 手动收藏
```

**关键实现选择：收藏夹不是新页面，而是 `filtered()` 的第一层条件。**

```js
if (S.fav) {
  const fav = FAVORITES.find(x => x.id === S.fav);
  if (fav && !favHas(fav, f)) return false;
}
```

这样类型页签、平台 chips、关键词搜索**天然可以叠加**——进了收藏夹还能继续筛，不需要写第二套渲染逻辑。这是最小改动，也最不容易出 bug。

**加入收藏夹（浮层，不是弹窗）**

右键菜单「加入收藏夹…」→ 浮层列出所有夹，多选勾选，底部「新建收藏夹」。

批量条也有「加入收藏夹」，一次处理所有选中项。

不做"拖拽进侧栏"：拖拽在浏览器里要处理 `DataTransfer`、跨容器命中、自动滚动，成本高且原型验证不了。**右键 + 批量条已经覆盖 90% 的场景。**

### 14.4 空状态必须分第四种

原型的空状态原本只有三种：空库 / 筛选无结果 / 索引为空。

**空收藏夹是第四种，不能套用第三种文案。** 「索引可能是空的，或者上次扫描中断了」会让人以为库坏了，实际上素材好好地在库里，只是没加进来。

| 场景 | 标题 | 按钮 |
|---|---|---|
| 空收藏夹 | 「旅行素材」还是空的 | 去全部素材挑 |
| 收藏夹内筛选无结果 | 「旅行素材」里没有匹配的素材 | 清除筛选 |

### 14.5 顺手修掉的一个数字矛盾

统计卡原来是「素材 / 图片 / 视频 / 总大小」，导致进收藏夹后显示 **5 素材 = 1 图片 + 2 视频**，剩下 2 个动图不见了。

现在改成「素材 / 图片 / 动图 / 视频」，四张卡能加得起来：`36 = 13 + 5 + 18`。总大小移到侧栏底部（本来就有），信息不丢。

> 这类"数字对不上"是最伤信任的缺陷——用户不需要懂技术就能发现，而且一旦发现就会怀疑所有数字。

### 14.6 落地要点（给开发）

| 项 | 做法 | 坑 |
|---|---|---|
| 数据表 | IndexedDB 新建 `fav` store：`{id, name, desc, order, ids[], sys}` | 别塞进 `file` 条目里（一条素材可能在多个夹，双向存容易不一致） |
| 成员关系 | **只在收藏夹侧存 ids**，素材侧不存 favs | 双向存必然对不齐；要查"这条在哪些夹"时扫 fav（几十个夹 × 几千条也很快） |
| 文件改名/移动 | 收藏夹里存的是 `relPath`，改名后会对不上 | 用 `hashes.json` 的 sha256 兜底：改名时按 hash 找到对应条目并更新 id |
| 删除收藏夹 | 只删 fav 记录，不碰文件 | UI 文案必须写明「素材文件不受影响」，否则用户不敢删 |
| 星标夹 | 不落盘，`starred` 变化时成员自动变 | 别把星标成员也写进 `ids`，会与 `starred` 产生两套真源 |
| 排序 | `order` 字段，星标固定 order=0 | 拖动排序在正式版做，原型用上移/下移 |
| 数量 | 侧栏计数要实时，星标变化后立刻更新 | 收藏后忘记 `render()` 是常见低级 bug |

### 14.7 没做但记下来的

- **拖拽进侧栏收藏夹**：跨容器拖拽成本高，先不做。
- **收藏夹封面墙**：Eagle 那样每个夹显示 4 张拼图封面。现在侧栏只有图标+名字，够用；如果以后收藏夹多到 20+，封面墙会显著提升辨识度。
- **收藏夹内手动排序**：现在按「保存时间/名称」排。如果收藏夹用来"讲一个顺序"（比如给别人演示），就需要手动排序。
- **智能收藏夹（规则型，不只星标）**：比如"B站 + 未看 + 4K"。这个能力很强，但要先有"已看/未看"字段，属于 V2。
