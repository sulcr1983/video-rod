## 一、数据库是怎么管的（先回答"JSON 还是什么"）

### 1.1 答案：IndexedDB，不是 JSON

| 存什么 | 存在哪 | 说明 |
|---|---|---|
| **素材元数据**（主索引） | **IndexedDB `vr-library` → `file` store** | 主键 `relPath`，5 个索引 |
| 缩略图 | IndexedDB → `thumb` store | 存 blob，按需单条取 |
| 设置 / 目录句柄 | `setting` / `handle` store | 句柄必须放 IDB（结构化克隆） |
| 操作日志 | `oplog` store | 重命名、删除流水 |
| **导出备份** | `index-{时间戳}.json` | 只是导出，不是真源 |
| 回收站清单 | F 盘 `_manifest.json` | 记录"哪些文件在回收站" |

**关键点：JSON 只用于"导出"和"日志"，不承担主索引。** 这是对的——如果用 JSON 当主库，5 万条就要整体读改写，每次改一条都要重写 20 MB，必然卡死。

### 1.2 表结构

```
file   keyPath: relPath
       索引: platform / creatorId / type / mtime / starred
thumb  keyPath: thumbKey   （blob + w + h）
```

索引设计是合理的：平台、作者、类型、时间、星标——正好对应界面上的筛选维度。

### 1.3 容量上限

- `manifest.json` 有 **`unlimitedStorage`** 权限 → 不受浏览器默认配额限制，可以用到磁盘满
- 实测（`file://` 环境，无该权限）配额是 **10 GB**

## 二、大数据量实测（这是重点）

### 2.1 实测环境与方法

- 用 Chromium 内核浏览器跑 `db-bench.html`
- 表结构、索引、字段**完全照抄 `js/library/db.js` 和 `indexer.js`**（每条 432 字节，含 title/platform/creatorId/sourceUrl/tags 等 15 个字段）
- 批量写入（每批 2000 条）→ `getAll()` 全量读 → 索引查询 → 内存 filter → 全量 DOM 渲染

### 2.2 结果

| 指标 | 1 万条 | 5 万条 | 判断 |
|---|---|---|---|
| 写入耗时 | 4.04 s（2,477 条/秒） | 15.66 s（3,193 条/秒） | ✅ 建库一次性，可接受 |
| **`getAll()` 全量读** | **203 ms** | **833 ms** | ✅ 能接受 |
| 元数据体积 | 4.1 MB（427 字节/条） | 20.6 MB（432 字节/条） | ✅ 很小 |
| **索引查询**（platform=x） | **53 ms**（命中 1,429） | **153 ms**（命中 7,143） | ✅ 很快 |
| **内存 filter**（关键词） | **11 ms** | **27 ms** | ✅ 很快 |
| **DOM 渲染全量卡片** | 拼串 299 ms + 布局 1.67 s = **1.97 s**，**13 万节点** | 拼串 822 ms + 布局 3.29 s = **4.11 s**，**65 万节点** | ❌ **瓶颈在这** |

### 2.3 结论：数据库完全撑得住，界面渲染撑不住

**这跟直觉相反。** 担心"数据库扛不扛得住"是对的，但实测下来数据库是最健康的一环：

- 5 万条元数据只有 20.6 MB，一次全读 833 毫秒
- 按索引查一个平台 153 毫秒
- 内存里筛关键词 27 毫秒

**真正的死穴是：5 万条要一次性塞 65 万个 DOM 节点，光浏览器布局就要 3.3 秒。**

按这个趋势线性外推（**未实测，因为 10 万条那档直接把测试跑崩了**）：
- 10 万条 ≈ 8 秒 + 130 万节点 → 页面基本不可用，滚动会卡成幻灯片
- 20 万条 ≈ 直接崩

### 2.4 真正吃空间的是缩略图，不是元数据

缩略图规格：最长边 **480 px**、WebP、质量 **0.72**（`thumbs.js:12-13`）。

| 规模 | 元数据 | 缩略图（按单张 25 KB 估） | 合计 |
|---|---|---|---|
| 1 万 | 4 MB | 250 MB | ~254 MB |
| 5 万 | 21 MB | 1.2 GB | ~1.2 GB |
| 10 万 | 42 MB | 2.5 GB | ~2.5 GB |

**结论：元数据可以忽略不计，缩略图是 50 倍于元数据的大头。** 有 `unlimitedStorage` 撑着，空间不是问题；但如果是木桶效应，先撞墙的是磁盘，不是数据库。

### 2.5 好消息：缩略图已经是懒加载

`ui.js:474` 用 `IntersectionObserver`，只加载视口附近的缩略图，`getThumb()` 也是单条取。**这个设计是对的，不用改。**

## 三、那要不要改数据库？怎么改？

### 3.1 不该做的（避免过度设计）

| 想法 | 为什么不该做 |
|---|---|
| 换 SQLite / 自己写文件格式 | IndexedDB 实测 5 万条 833 ms，够用。换库要重写全部读写，收益为零 |
| 加全文检索引擎 | 5 万条内存 filter 只要 27 ms，加索引反而增加同步复杂度 |
| 分库分表 | 单库 20 MB，没有分片必要 |

### 3.2 该做的（按优先级）

| # | 改什么 | 为什么 | 工作量 |
|---|---|---|---|
| **1** | **虚拟滚动**：只渲染视口内约 50 张卡片，滚到哪渲到哪 | 这是唯一真正的瓶颈。5 万条 4.11 s → 目标 < 100 ms | 中 |
| 2 | **首屏分页**：`getAllFiles()` 改成先取 200 条，其余滚动时再取 | 5 万条 833 ms 的读取对首屏还是慢 | 中 |
| 3 | 缩略图降规格（480→360 px，质量 0.72→0.65） | 5 万张能省约 40% 空间 | 低 |
| 4 | 「重建索引」加进度条与可取消 | 5 万条要 15.66 秒，用户会以为卡死 | 低 |

**判断：数据库选型不用动，动界面渲染方式就行。** 这是"最小改动、最大收益"的选择。

### 3.3 一个必须提醒的时间窗

`getAll()` 改成"分页取"之后，**依赖"全量内存数组"的现有代码会全部失效**——`ui.js` 的 `all` 数组被 `renderSide()`、`renderOverview()`、`renderCreators()`、`counts()`、`sorted()` 同时依赖。

所以虚拟滚动不是"加个组件"，是**要把"全量内存"模型改成"按需取数"模型**。这是本轮改动里工作量最大的一块，不能塞进"换皮"批次，必须单独立项。

## 五、界面与 CSS 的决定（不再问你，我定）

结合影响分析与实测，定三条：

| 项 | 决定 | 理由 |
|---|---|---|
| **CSS 改法** | **令牌替换 + 逐组件改**，不整体重写 | 现文件 2981 行、30+ 处动态 class。令牌替换能拿到大部分视觉提升且可单独回退 |
| **视频控件** | **不引 Media Chrome**，在原 `libVideoCtl` 上补键 | 已有 8 个控件并接好事件，引库等于替换能用的东西 |
| **动图** | **先验原生 `ImageDecoder`**，能覆盖三格式就不引库 | 少一个依赖 |
| **网格排版参考** | 照 Eagle / TagStudio 的密度与信息层次；**不自创布局** | 你说的"别造轮子"我照办 |

**唯一需要提前说清的**：如果要做虚拟滚动，网格的 DOM 结构会被重写（现在是 `innerHTML` 一次性拼），这跟"只换皮"是两类改动。我会把它排成独立批次，不和视觉改造混在一起。

## 六、一句话总结

**数据库没问题——5 万条只占 20 MB、全读 833 毫秒、查一个平台 153 毫秒。真正的墙是界面：5 万条要渲染 65 万个节点、光布局 3.3 秒。**

所以不用换数据库，要换的是"一次渲染全部"这个做法。而这件事的工作量比想象大，因为它会把"全量内存数组"的模型整个换掉，不能顺手做。

功能层面：**下载这一块已经真做完了（IG 和 YouTube 未验），资源库差的是动图、标签界面、溯源、以及虚拟滚动。** 假实现只有一处（分辨率写死），改一行就能补。
