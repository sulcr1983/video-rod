## 一、五道关详解

### 关 1 · 许可证（GPL-3.0，硬约束，无操作空间）

- fork 自猫抓（xifangczy/cat-catch，GPL-3.0），衍生作品**必须以同协议开源**：
  - 公开全部源码（含我们的全部增量，不能只开源一部分）
  - 保留猫抓原版权声明与署名，README 标注「基于猫抓修改」及上游地址
  - Chrome 商店分发同样属于 GPL 意义上的「传递」→ 商店页须提供源码获取方式（仓库链接即可）
- **利好**：猫抓自己就在 Chrome 商店上架——GPL 软件上商店有先例，路是通的
- **利好**：我们的增量代码全部自研（mux.js=Apache-2.0、youtubei.js=MIT、Floating UI=MIT、思源字体=OFL，均可商用 redistribution，保留各自许可声明即可）

### 关 2 · 高风险功能（需要动刀裁剪）

| 功能 | 风险等级 | 风险说明 | 发布版建议 |
|---|---|---|---|
| B站大会员清晰度下载 | 🔴 高 | 绕过付费墙，国内法律风险最高（著作权，非仅平台条款） | **裁掉或默认锁死**；自用版保留 |
| YouTube 下载 | 🟡 中 | 违反 YT 条款；商店对该类扩展态度反复，投诉即可能下架（nsig 属混淆参数非 DRM，有 Video DownloadHelper 在架先例） | 可保留，但必须备好 GitHub 兜底分发渠道 |
| 抖音/小红书/X 批量 | 🟡 中 | 反爬对抗是持续消耗，站点一改版就坏，差评随来 | 保留，接受维护节奏 |
| fxtwitter 第三方解析 | 🟡 中 | 大量用户会放大对第三方服务的调用，服务方可能限流 | 文档化披露；中期自建或换官方 API |

### 关 3 · Chrome 商店审核

- 权限组合（`<all_urls>` + `webRequest` + `scripting` + `declarativeNetRequest` + `downloads`）**必触发人工深度审核**，首次上架等数周是常态
- 必须补：隐私政策页（可放 GitHub Pages）、数据使用披露——如实写「不上传用户数据；X 解析调用 fxtwitter 公开服务仅发推文 ID」
- **天生合规项**：零构建、无远程代码加载、无混淆代码——商店最严的两条红线（remote code / misleading）我们不沾
- 开发者注册：$5 一次性，可忽略

### 关 5 · 维护成本（发布容易，养发布难）

- **站点适配是持续消耗**：B站/YouTube/小红书/抖音任一改版即坏，用户差评立竿见影。上游猫抓在高频维护这些，fork 后**要不要跟上游同步**是长期决策（建议：定期 rebase 上游嗅探内核，保留我们的库与 UI 层）
- 用户 issue / 评价 / 邮件需要人接
- 版本节奏：商店审核流程会拖慢修复上线速度（对比自用即时 reload）

## 二、发布三步走（每步可停）

| 步 | 动作 | 成本 | 拿到什么 |
|---|---|---|---|
| 1. GitHub 开源试水温 | 脱敏 + 改品牌 + 公开仓库 + Releases 提供 zip | 脱敏 1-2 天 | 真实用户反馈、star 水温；不上商店零审核 |
| 2. 裁剪后上商店 | 砍大会员清晰度、补隐私政策、商店素材（截图/描述/类别） | 2-3 天 + 审核等待 | 正式分发渠道、自动更新 |
| 3. 视反馈决定推广力度 | 文档站、多语言、Firefox 移植（sidePanel 需改造，polyfill 已有基础） | 持续 | 用户规模 |

- 想借发布倒逼工程质量（公开即压力测试）
