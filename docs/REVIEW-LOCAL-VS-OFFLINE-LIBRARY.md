# 评审：本地媒体库 vs 离线媒体库（两个都要，怎么做）

> 日期：2026-11-17 ｜ 触发：苏哥「本地媒体库和离线的，一起做」+「单独做个 html 页面只查看不管理行不行」
> 方法：先核实两边真实实现，再给方案

---

## 一、先澄清一个事实（我之前表述有误）

### 抖珍藏的 `本地库.html` 到底怎么来的

完整链路（代码实证）：

```text
ui.douzhencang.com（远端 iframe）
   │ postMessage({direction:203, ...content})
   ▼
r.js（rl.html 的桥）
   │ if (origin === 'https://ui.douzhencang.com') parent.postMessage({direction:203,...c}, 'https://www.douyin.com')
   ▼
s.js → ao() → case 4: We(a)
   ▼
Ue = { archiveHtml: '<html>…</html>', appJs: '…', rootReadme: '…' }
   ▼
Ge('archiveHtml') → 写文件 <用户目录>/本地库.html
```

**准确表述**：

| 环节 | 是否本地 | 说明 |
|---|---|---|
| **生成页面内容** | ❌ **远端** | HTML 字符串由 `ui.douzhencang.com` 下发 |
| **写入磁盘** | ✅ 本地 | `Ge()` 写到用户选的目录 |
| **打开后运行** | ✅ **完全本地** | 就是个静态 HTML，不再联网 |

**所以你的判断是对的**：抖珍藏的库页**打开后确实是本地的**。我之前说「远端下发的页面」只对**生成环节**成立，对**使用环节**不成立——**表述不准确，这里更正**。

### 对我们的启示

**关键不是「页面从哪来」，而是「打开后需不需要网络」。**

抖珍藏的做法有个隐患：**内容靠远端下发，如果服务停了，新用户就生成不出这个页面**（已有文件的用户不受影响）。

**我们不该这样**——我们的离线页应该**由扩展自己生成**，不依赖任何服务。

## 二、回答你的问题：单独做个 HTML 只查看不管理，行不行？

**行，而且这是正确做法。**

### 2.1 为什么「只查看不管理」是对的

| 能力 | 扩展内库页 | 离线 HTML |
|---|---|---|
| 浏览 / 搜索 / 筛选 | ✅ | ✅ |
| 看图片 / 播视频 | ✅ | ✅ |
| **删除 / 重命名 / 移动** | ✅ | ❌ **做不到** |
| **回收站恢复** | ✅ | ❌ |

**根本原因**：浏览器外的 HTML **没有文件系统写权限**（`showDirectoryPicker` 只在扩展/HTTPS 上下文可用）。强行做管理，只能得到「点了没反应」。

**所以：查看器只读，是技术约束下的正确设计，不是妥协。**

### 2.2 但可以做「有限交互」

只读不等于死板。以下这些**不需要写权限**，可以做：

| 功能 | 是否可行 |
|---|---|
| 搜索（标题/作者/文件名） | ✅ |
| 按平台/作者/类型筛选 | ✅ |
| 按大小/时间/名称排序 | ✅ |
| 缩略图网格 / 列表切换 | ✅ |
| 点开大图 / 播放视频 | ✅（用相对路径） |
| 复制原帖链接 | ✅ |
| **「在文件夹中打开」** | ❌（浏览器外无此能力） |
| **删除 / 改名 / 移动** | ❌ |

### 3.2 **重大发现：导出功能已经存在**

`js/library/settings.js:933-1000` 已有完整的「导出整包」：

```js
/* 口径：
 *   · 导出 = 只打包 `_library/`（索引 + 收藏夹 + 缩略图），不碰素材本体
 *   · 恢复 = 从已授权的目录读 `_library/index.json` 重放，不删任何东西
 */
```

现有能力（已核实）：

| 能力 | 实现 |
|---|---|
| 递归列文件 | `listFiles(dir, prefix)` |
| **零依赖 zip 打包（STORE 不压缩）** | `makeZip(entries)` |
| 触发下载 | `downloadBlob(blob, '_library-backup.zip')` |
| 导出内容 | **`_library/`（索引 + 收藏夹 + 缩略图）** |

**这意味着离线库的成本比预想低得多**——打包、缩略图、索引全都有了，**只缺「查看器 HTML」**。

### 3.3 还缺什么

| 缺口 | 影响 | 解法 |
|---|---|---|
| **没有查看器 HTML** | 导出的 zip 只能用扩展恢复，不能直接看 | 新增 `offline-export.js` 生成 |
| 缩略图在 zip 里但 HTML 不知道路径 | — | 查看器按 `_library/thumbs/*.webp` 读 |
| **素材是绝对路径** | 换电脑失效 | 改用相对路径 + 可选「含原文件」 |
| 没有「服务器已删」标记 | 离线页看不出 | 可选：带 `disappeared` 快照 |

## 四、方案：双模式，一份数据

```text
┌─────────────────────────────────────────────┐
│  library.html（现有，不动）                  │
│  管理入口：增删改查 / 批量 / 回收站 / 迁移    │
│  数据源：IndexedDB（实时）                    │
└──────────────────┬──────────────────────────┘
                   │ 点「导出离线库」
                   ▼
┌─────────────────────────────────────────────┐
│  离线包（用户选的目录）                       │
│  ├── 本地库.html      ← 只读查看器（自包含）  │
│  ├── index.json       ← 快照（schema 2）     │
│  ├── thumbs/*.webp    ← 缩略图（可选）        │
│  └── 说明.txt         ← 怎么用               │
└─────────────────────────────────────────────┘
```

### 4.1 关键设计决定

| 决定 | 理由 |
|---|---|
| **离线页由扩展自己生成** | 不依赖远端服务（对比抖珍藏的隐患） |
| **不改造 `app.js`** | 它依赖 10 类 `chrome.*`（13+8+6 处），改造成本 > 重写 |
| **新写 `viewer.html`** | 纯静态，零 `chrome.*`，只读快照 JSON |
| **快照格式不变** | `schema:2` 已够用 |
| **缩略图可选** | 默认包含（体积小），原文件可选（体积大） |

### 4.2 离线页的技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 数据加载 | `fetch('index.json')` | 同目录，`file://` 下 Chrome 可能拦截 → **改为内联到 HTML** |
| 图片显示 | `thumbFile` 相对路径 | 同目录，直接可用 |
| 视频播放 | 相对路径 `<video>` | 需「含原文件」才可用 |
| 搜索/筛选 | 纯前端 JS | 无依赖 |
| 样式 | 内联 CSS | 单文件 |

**关键约束**：`file://` 下 `fetch('index.json')` 会被 CORS 拦截。**解法：把 JSON 内联进 HTML 的 `<script type="application/json">`。**

## 六、两个必须说清的风险

### 6.1 离线页会「过时」

导出后，素材增删改都**不会自动同步**到离线页。用户需要**重新导出**。

**缓解**：导出时在包里写 `导出时间` 与 `条目数`，查看器顶部显示「数据截止：2026-11-17 22:30」。

### 6.2 离线页路径依赖

默认方案下，`thumbFile`/`relPath` 指向**导出时的库根**。如果库移动了，图片会失效。

**缓解**：导出时用**相对路径**（相对于导出包位置），而不是绝对路径。这样整个库目录一起拷走也能用。
