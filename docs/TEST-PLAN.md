# 钓鱼竿 · 测试方案（v1，2026-11-12）

> 起因：苏哥「感觉老是出问题，能不能出个测试方案，看看人家怎么做的」。
> 结论先说：**问题不在"没有测试"，而在"测试跑不起来、跑了没人看、红了也没人管"**。
> 仓库里已有 31 个纯逻辑单测（775 条断言，全绿）和 9 个界面套件 —— 但改一行代码要手敲 9 条命令，
> 所以实际没人跑。方案的第一件事不是加测试，是**给一个 40 秒的入口**和**一条会红的线**。

## 二、业界怎么做（对照）

Chrome 扩展测试的公开实践基本收敛成三层（参考 TabbyTab、Custom-JavaScript、Perplexity 扩展、以及 Chrome 官方扩展示例）：

| 层 | 做法 | 工具 | 我们的对应 |
|---|---|---|---|
| L1 纯函数 | 把逻辑从 `chrome.*` 里剥出来，Node 里直接跑 | Jest / Vitest | **已有且更好**：用 `new Function` 从源文件切函数，不起浏览器 |
| L2 扩展页集成 | 加载扩展，打开 `chrome-extension://…` 页面，操作 DOM、收发消息 | Playwright / Puppeteer + `--load-extension` | 自研 CDP 驱动（等价，且能直连 SW） |
| L3 真实站点 E2E | 真浏览器 + 真登录态 + 真站点，跑核心用户路径 | Playwright + 固定测试账号 | 有脚本，无编排、无基线 |
| 门禁 | push 跑 L1，main/nightly 跑 L2/L3，红就不发 | GitHub Actions / Jenkins | **缺** |
| 视觉回归 | 截图与基线像素比对 | jest-image-snapshot | **缺**（只有截图存档，无基线） |
| 稳定化 | E2E 串行（防实例竞争）、每例前复位状态、flaky 显式登记 | `--runInBand` / fixture | **缺**（本次补前两项） |

我们的差异：L1 覆盖率远高于同类项目（775 条断言），**短板全在编排与门禁**。

## 三、方案：四层 + 三档 + 一条门禁线

### 3.1 分层与职责

```
L4  手工验收（人）：装完/换皮/新站点首测/观感与文案
      ↑ 每次发版前 10 分钟清单（§5）
L3  真实站点 E2E（机）：B站 / 小红书 / 抖音 / 微博 / 通用+HLS
      ↑ 发版前、每周一次；有风控，串行 + 随机抽验
L2  界面套件（机）：扩展页 DOM/消息/流程，隔离实例，不碰真实库
      ↑ 每次改前端/后台都要跑（约 2 分钟）
L1  纯逻辑单测（机）：命名/路径/去重/选源/图片/持久化
      ↑ 每次改代码都跑（40 秒）
```

原则：**下层不确定，不上层白跑**。L1 红了直接停，不要浪费 3 分钟起浏览器。

### 3.2 三档执行（唯一入口）

```bash
python tools/health-check.py            # 冒烟：改完代码自检，约 40 秒
python tools/health-check.py --full     # 全量：发布前必跑，约 4 分钟
python tools/health-check.py --live     # 全量 + 真实站点（需登录态，有风控）
```

每一步做什么：

| # | 步骤 | 内容 | 拦什么 |
|---|---|---|---|
| 1 | 源码语法 | 130 个 js `node --check` | 语法错、半截改动 |
| 2 | manifest | JSON 可解析、name/version/MV 齐 | 装不上 |
| 3 | 断言契约 | 35 个测试脚本引用的 DOM id 是否真实存在 | **测试腐烂**（本次新增） |
| 4 | 单元测试 | 冒烟 9 个 / 全量 32 个（1300+ 条断言） | 逻辑回归 |
| 5 | 界面套件 | 冒烟 2 个 / 全量 10 个（隔离实例） | 界面/消息/流程回归 |
| 附 | 发布物 | dist 与 zip 是否存在 | 发出去的包是旧的 |

产出：终端一句话结论（**可以发 / 不能发**）+ `deliverables/test-runs/health-<时间>.md`。

### 3.3 门禁规则（一条线，不许绕）

| 场景 | 必须过 | 不过怎么办 |
|---|---|---|
| 改代码（每次） | 冒烟 6 项 | 修到绿再继续，不许「先提交后面再看」 |
| 发版 / 打包 | 全量（含 10 套件） | 红即停；确属他人未完成 → 走 baseline 登记 |
| 新站点适配 / 大改 | 全量 + L3 该类站点真机 + 手工清单 | 同上 |

**已知失败基线**（`tools/health-baseline.json`）：
并行会话正在改的功能（当前：`stage-rewrite`、`skin`）登记为已知失败，不算本次回归；
**新的**失败才拦发布。这样红是有意义的红，不会变成「反正一直红」。

```bash
python tools/health-check.py --full --update-baseline
# 只在「确认这些失败不是本次改动引入」时才用，登记理由会写进 json
```

## 五、手工验收清单（L4，发版前 10 分钟）

机跑不出「好不好用」，这 8 条每次发版人过一遍（截图存档到 `deliverables/assets/`）：

1. **装/重载**：`edge://extensions` 重新加载，无红色错误，图标在
2. **B 站**：单P 一键下载 → 有进度 → 落 `B站/<作者>/`；再点一次 → 提示「已下过」；换清晰度 → 能下
3. **小红书**：图文页侧栏 → 只勾实况 → 落 `jpg + _live.mp4` 两件套
4. **图片**：任意图站 → 侧栏切「大 ≥1200」→ 不混入「尺寸未知」；点「未知」→ 只剩未知；
   微博/图墙页点 popup「抓图」→ 张数与侧栏接近、每行有真实尺寸、无裂图
5. **资源库**：左上角路径卡 → 弹文件夹选择器 → 取消无副作用；右侧箭头 → 进设置
6. **资源库**：详情页预览图片/视频各一次；删除 → 回收站 → 恢复
7. **换皮**：popup / 库页 / 设置 / 安装页 四屏颜色一致（舞台金、暖白字），无白底残留
8. **文案**：四个页面无第三方平台名（不宣传）、无「点击更换目录」等过期提示

## 六、缺陷闭环（为什么"修过的还会再坏"）

每个用户报障必须走完四步，缺一步不算关闭：

```
① 复现成脚本   →  tools/test-*.py 里最小可跑片段（不许只在聊天里描述）
② 断言化      →  至少 1 条能红的断言；写进 TESTING.md §4.x 并登记到 health-check
③ 进套件      →  单测能覆盖就进 L1；必须真机就进 L3，并写进 TESTING 的「改这里要跑」
④ 反证        →  临时把修复回退，确认断言真的红（防止"测试永远绿"）
```

本次 B 站 bug 就是①~③都做了：`tools/test-bili-source.py` 12 条，其中 T2c（同集二次必须 skipped）在修复前是红的。

### 视觉基线怎么用

```bash
python tools/visual-baseline.py --update      # 改了样式、确认是"想要的改动"之后刷新基线
python tools/visual-baseline.py               # 平时比对（health-check --full 会自动跑）
```

> 三屏都做了「起跑线固定」：popup 的一次性引导浮层被钉成已读、options 的动态下载路径文案被钉成固定串。
> 不钉的话会得到 0.2%~24% 的**假差异**（都实测踩过）。
> 资源库主界面由数据驱动（树计数/卡片数每天变），不做像素基线，结构与交互交给 stage-rewrite / e2e-buttons。

### 真实站点清单怎么用

```bash
python tools/live-sites.py --only local   # 无网络也能跑（本地夹具）
python tools/live-sites.py                # 全部（含 B站 + 3 个真站探活）
```

> `required: true`（本地夹具、B站公开视频）失败会拦；`required: false`（小红书/抖音/微博探活）
> 失败只记 WARN —— 登录态、风控、站点改版都会让它红，不该因此挡住发版。
