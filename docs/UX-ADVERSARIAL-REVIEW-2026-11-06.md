# video-rod 对抗性审查报告

> 日期：2026-11-06 ｜ 视角：高级工程师，主动挑毛病
> 方法：读代码 + 真机实测（Edge 9480，真实库 39 条），每条都给出**位置 / 用户影响 / 修法 / 优先级**。
> 不写「整体不错」这类空话，只列会让人卡住、误操作、或效率低下的地方。

**优先级定义**
- **P0**：会让用户丢数据、误操作、或功能直接不可用
- **P1**：高频路径上的明显不顺，用户每天都会遇到
- **P2**：体验打磨，影响观感与效率
- **P3**：工程债，影响后续维护

## 一、P0 · 会丢数据 / 误操作

### 1. 删除后没有撤销，只有「回收站」这条暗路

**位置**：`js/library/app.js` `pvDelete` / `batchTrash`；`library.html#drawer`

**现状**：确认框文案写着「文件还能恢复」，但恢复入口藏在左侧底部一个不显眼的「回收站 3」按钮里，且**删除后没有任何 toast 提供「撤销」**。

**用户影响**：
- 用户误删 20 条，第一反应是找 Ctrl+Z——**没有**。
- 只有知道「回收站」在哪的人才能找回。新用户会以为真删了。
- 批量删除后如果关了页面，更容易慌。

**实测**：删除流程无 `undo` 字样、无撤销按钮（`grep undo` 零结果）。

**建议**：
1. 删除后 toast 增加「撤销」按钮，5 秒内可一键恢复（业界标准：Gmail / Notion / macOS 废纸篓）。
2. 回收站入口移到**显眼位置**（顶栏），并显示数量徽标。
3. 参考：`sonner` / `react-hot-toast` 的 undo toast 模式（本项目零依赖，用现有 toast 扩展即可，约 30 行）。

**优先级：P0**

---

### 2. 批量删除 / 移动没有「进行中」状态，界面会假死

**位置**：`js/library/app.js` `batchTrash` / `VRMovePicker.doMove`

**现状**：批量操作是 `for` 循环 + 逐个 `await`，**期间没有任何进度提示**。删 50 条时界面完全无反馈，用户会以为卡死并重复点击。

**用户影响**：
- 重复点击 → 重复确认框叠加。
- 大文件移动（几百 MB）时无进度，用户不知道要等多久。
- 中途失败只报「失败 N 项」，**不说是哪几条**。

**建议**：
1. 加一个轻量进度条（复用 `image-batch.js` 的底部进度条模式）。
2. 失败项列出文件名，可点击定位。
3. `MV.busy` 已有标志位，但没有禁用按钮——补上 `disabled` 与 loading 文案。

**优先级：P0**

---

### 3. 「全部恢复」没有二次确认，可能覆盖已有文件

**位置**：`js/library/app.js` `openTrash` → `dwRestoreAll`

**现状**：回收站的「全部恢复」直接执行，无确认、无冲突预检。

**用户影响**：如果原路径已有同名文件（用户后来重新下载过），恢复会失败或覆盖，**用户不知道发生了什么**。

**建议**：
1. 恢复前预检冲突，列出「N 项会被覆盖/跳过」。
2. 参考 `VRTrash.moveFile` 已有的 `noOverwrite` 语义，明确策略并在 UI 说明。

**优先级：P0**

## 二、P1 · 高频路径上的明显不顺

### 4. 搜索无防抖，大库打字卡顿（实测数据）

**位置**：`js/library/app.js:794`

```js
search.addEventListener('input', function (e) { S.q = ...; render(); });
```

**实测**：
| 库规模 | 单次按键重渲染 |
|---|---|
| 39 条 | 3 ms（无感） |
| 5 000 条 | **64 ms**（连续打字明显掉帧） |
| 50 000 条 | 预计 100ms+（不可用） |

**用户影响**：库一大，每敲一个字符卡一下；中文输入法组字时更糟（每个拼音都触发）。

**建议**：
1. 加 150–200ms 防抖（`setTimeout` 清空前一次，约 8 行）。
2. 输入法组字期间跳过（监听 `compositionstart/end`）。
3. 参考：`lodash.debounce` 的语义，但**不引依赖**，手写足够。

**优先级：P1**

---

### 5. 库页首屏没有加载态，2 秒白屏

**位置**：`js/library/app.js` `load()` → `render()`

**现状**：`boot()` 要等 `loadFavs → ensureRoot → refreshPermState → load`，全部完成后才渲染。中间是**纯空白**（只有侧栏骨架）。

**实测**：`window.__vrBoot` 显示 `load:39` 前有约 2 秒空窗。

**用户影响**：
- 用户以为扩展坏了 / 库空了。
- 慢盘或大库时更明显。

**建议**：
1. 骨架屏（skeleton cards），或至少居中「正在加载素材…」。
2. 参考：Pinterest / Eagle 的骨架屏模式。
3. 约 20 行 CSS + 一个占位分支。

**优先级：P1**

---

### 6. 「移动到…」文件夹一多就没法找

**位置**：`js/library/move-picker.js`

**现状**：只支持「进入 / 上一级 / 新建」，**没有搜索框、没有面包屑点击、没有最近使用**。

**用户影响**：库里有几十个平台/作者目录时，要从根一层层点进去，移动一条素材可能要 5–6 次点击。

**建议**：
1. 加搜索框（过滤当前层 + 递归匹配，复用 `render()` 的 dirs 数组）。
2. 面包屑可点击回跳（当前只有「上一级」）。
3. 「最近移动到的文件夹」置顶。
4. 参考：VS Code 命令面板 / macOS 保存对话框的路径补全。

**优先级：P1**

---

### 7. 批量下载进度在资源库页完全不可见

**位置**：`js/library/app.js`

**现状**：`vrBulkProgress` 广播只发到**原页面**（微博/X 主页），资源库页收不到。用户在库里等下载完成，**没有任何反馈**。

**用户影响**：下载 20 个视频时，用户不知道进度、不知道是否卡住、不知道失败几条。

**建议**：
1. 资源库页监听 `vrBulkProgress`，底部显示全局进度条。
2. 完成后 toast「已入库 N 项」，点击可跳到新素材。

**优先级：P1**

---

### 8. 空态没有引导，新用户不知道下一步

**位置**：`js/library/app.js` `renderEmpty`

**现状**：只有一句「还没有素材」+「清除筛选」。

**用户影响**：首次安装、或选了空目录后，用户不知道：
- 要先授权目录
- 要去网页下载才会入库
- 可以「重新扫描」

**建议**：
1. 区分三种空态：**未授权** / **目录为空** / **筛选无结果**，各给一条明确行动按钮。
2. 参考：Eagle 首次启动的「拖入文件 / 选择文件夹」双入口。

**优先级：P1**

---

### 9. 详情页「定位」在无绝对路径时不可用，且提示含糊

**位置**：`js/library/app.js` `pvReveal`

**现状**：FSA 自选文件夹的条目 `absPath` 为空，点「定位」只 toast「这条没有本地路径，无法定位」。

**用户影响**：用户不知道为什么没有路径，也不知道怎么才能有。

**建议**：
1. 文案改成可操作：「当前库未记录绝对路径，可在设置里填写路径以便定位」。
2. 或用目录句柄逐级定位（`VRFile` 已有读句柄能力，可扩展为打开所在目录）。

**优先级：P1**

## 三、P2 · 体验打磨

### 9.5 重命名不做重名校验，能造出两条同名卡片

**位置**：`js/library/app.js` `renameOk`

**现状**：只校验「不能为空」，**不校验是否与已有条目的 `displayName` 重复**。

**用户影响**：
- 用户把 A 改名成和 B 一样的名字，库里出现两张同名卡片，**无法区分**。
- 再想改回来，得先找出哪张是哪张。
- 批量场景下更容易撞名（如把一批都改成「旅行」）。

**实测**：`renameOk` 里只有 `if (!v) { toast('文件名不能为空'); return; }`，无任何重名检查。

**建议**：
1. 提交前查 `FILES.some(f => f.id !== renRel && f._title === v)`，命中则提示「已有同名素材，是否继续？」。
2. 或自动加后缀 `(2)`（但会加剧同名问题，不如直接提示）。
3. 参考：macOS Finder 重命名的「已存在同名项目」提示。

**优先级：P1**

---

### 10. 死代码：旧的 `#ctx` 右键菜单（15 个按钮）仍在 HTML 里

**位置**：`library.html:474` 附近

**现状**：`#ctx` 菜单完整存在（预览/打开/复制/星标/收藏/重命名/移动/回收站），但**没有任何 JS 引用它**——实际生效的是 `ctx-menu.js` 渲染的 `#vrCtxMenu`。

**用户影响**：不会直接出错，但：
- 增加维护困惑（改错地方）
- 增加 DOM 体积
- 样式可能冲突

**建议**：删除 `#ctx` 整块及关联 CSS（`css/library.css` 的 `.ctx` 规则）。约 -60 行。

**优先级：P2**

---

### 11. 回收站计数硬编码 `3`

**位置**：`library.html:139` `<b id="trashCnt">3</b>`

**现状**：初始值是 `3`，要等 JS 算完才纠正。首帧会闪一下错误数字。

**建议**：初始值改为 `0` 或空，用 `hidden` 控制显示。

**优先级：P2**

---

### 12. 搜索框没有「清除」按钮与快捷键提示

**位置**：`library.html#search`

**现状**：只能手动全选删除；`/` 聚焦已实现但无提示。

**建议**：
1. 输入非空时显示 `×` 清除。
2. placeholder 补一句「按 / 聚焦」。
3. 支持 `Esc` 清空。

**优先级：P2**

---

### 13. 卡片缺少「已下载/重复」的即时视觉反馈

**位置**：`js/library/app.js` `card()`

**现状**：`isRef` 有「引用」角标，但用户从网页重复下载时，库里**看不出「这条已经有了」**。

**建议**：命中 `vrFindExistingMedia` 时，toast 明确「已存在：xxx」，并高亮库中对应卡片（滚动定位 + 闪烁）。

**优先级：P2**

---

### 14. 批量条按钮无「已选 N 项」的上下文操作

**位置**：`library.html#batchbar`

**现状**：只有「全选/反选/清除/收藏/移动/删除/退出」，**没有「反选可见项」或「按类型选」**。

**用户影响**：想「只删视频」时只能手动点。

**建议**：加一个下拉「按类型选择（图片/视频/音频）」。

**优先级：P2**

---

### 15. 键盘可达性不足

**实测**：`library.html` 里 `tabindex`/`aria-*` 共 15 处，卡片虽有 `tabindex="0"`，但：
- 侧栏树节点是 `<button>`（好）
- **卡片内的复选框、右键菜单项**缺少焦点管理
- 焦点在预览层时，`Tab` 会跑到背后的页面

**建议**：
1. 预览层加 `focus trap`（打开时把焦点限制在层内）。
2. 右键菜单已有 ↑↓/Enter/Esc（好），补 `Tab` 循环。

**优先级：P2**

## 四、P3 · 工程债

### 16. `background.js` 4545 行、`app.js` 1904 行

**现状**：单文件过大，改一处要翻很久，且容易出作用域 bug（本轮已发生 2 次：`ask` 未定义、`fav-star` 找不到）。

**建议**：
- 先补测试再拆（BACKLOG D-02 已记录）。
- 优先拆出：`vrBulkDownload` / `vrXhs*` / DNR 规则管理 / 命名与路径。

**优先级：P3**

---

### 17. 274 处空 `catch {}`

**实测**：`grep` 统计全仓库 274 处 `catch (e) { /* 忽略 */ }`。

**风险**：这是本轮多个 bug 的温床——异常被吞掉，用户只看到「没反应」。

**建议**：
1. 关键路径（下载、入库、写盘）的 catch 至少 `console.warn` 带上下文。
2. 建立约定：**静默 catch 必须写明为什么可以忽略**。

**优先级：P3**

---

### 18. 没有统一的错误提示层

**现状**：有的地方 `toast`，有的 `alert`（原生），有的只 `console.warn`。

**建议**：统一走 `toast(msg, level)`，`level` 区分 info/warn/error，错误带「重试」动作。

**优先级：P3**

---

## 五、功能性建议（可增强）

### 19. 缺少「下载队列」全局视图

现在下载分散在：popup 面板、页面浮层、库页批量、YouTube 小窗。**没有一个地方能看到「所有正在下的任务」**。

**建议**：库页加一个「任务」抽屉，聚合所有进行中/已完成/失败任务，支持重试与取消。
参考：IDM 的任务列表、qBittorrent 的传输面板。

**优先级：P1（功能缺口）**

---

### 20. 缺少「重复文件清理」入口

已有 `dedup.js`（SHA-256 + 引用计数），但**没有 UI 让用户主动扫描并合并重复**。

**建议**：设置页或库页加「扫描重复」按钮，列出内容相同的组，支持「保留一份 + 其余转引用」。

**优先级：P2**

---

### 21. 标签体系缺少「批量打标」与「标签筛选面板」

已有标签 CRUD（`pvTagAdd`），但：
- 批量条没有「加标签」
- 左侧树没有「按标签筛选」

**建议**：批量条加「加标签」；侧栏加标签云，点击筛选。

**优先级：P2**

## 六、我建议的修复顺序

| 顺序 | 事项 | 理由 |
|---|---|---|
| 1 | 删除撤销 + 回收站入口显眼（#1） | 直接防止丢数据 |
| 2 | 批量操作进度 + 失败明细（#2） | 高频且易误判卡死 |
| 3 | 全部恢复的冲突预检（#3） | 破坏性操作 |
| 4 | 重命名重名校验（#9.5） | 会造成无法区分的同名卡片 |
| 5 | 搜索防抖（#4） | 一行改动，大库收益明显 |
| 6 | 首屏骨架屏（#5） | 首次观感 |
| 7 | 移动选择器搜索 + 面包屑（#6） | 高频操作效率 |
| 8 | 空态分场景引导（#8） | 新用户留存 |
| 9 | 删死代码 + 修硬编码（#10/#11） | 低成本清理 |
